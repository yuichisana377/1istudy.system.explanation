```python
def _task_id_of_plan(plan: dict) -> str:
    """フロント（StudyLog.js）の `${p.date}_${p.subject}_${p.content}` と全く同じ規則でIDを作る"""
    return f"{plan.get('date')}_{plan.get('subject')}_{plan.get('content')}"
```
- 課題（予定の中でも、達成/未達成の管理対象になっているもの）を一意に識別するためのID文字列を、予定データから作る関数です。予定自体には専用のIDが振られていないため、代わりに「日付＋科目＋内容」を組み合わせた文字列をIDの代わりに使っています。コメントにある通り、これはフロント側（`StudyLog.js`）で組み立てているIDの規則と**完全に一致させる必要がある**重要な関数です。サーバー側とフロント側で1文字でも規則がズレると、同じ課題なのに別のIDとして扱われてしまいます。

```python
def find_task_points(guild_id: int, task_id: str):
    """
    task_id に対応する予定（課題）をサーバー側の plans から探し、
    本来のポイント数を返す。クライアントが自己申告する points は一切信用しない。
    見つからない場合は None を返す（＝そもそも存在しない課題IDとして扱う）。
    """
    plans = load_plans(guild_id)
    for p in plans:
        if _task_id_of_plan(p) == task_id:
            pts = p.get("points")
            return pts if pts is not None else DEFAULT_TASK_POINTS
    return None
```
- **セキュリティ上、重要な関数です**。コメントにある通り、「この課題をやったから〇〇ポイントもらえるはず」という申告を、ブラウザ側（クライアント）からの自己申告のまま信用してはいけません。もしそうしてしまうと、悪意のあるユーザーがブラウザの開発者ツール等でリクエストの中身を書き換え、実際には1ポイントの課題なのに「1000ポイント」と偽って送りつける、といった不正が可能になってしまいます。
- そのため、`find_task_points`は`task_id`だけを受け取り、**本来何ポイントの課題だったのかを、サーバー側の`plans`データから改めて調べ直します**。クライアントから送られてきた`points`という値そのものは、この関数の中では一切参照されていません。呼び出し側（後述の課題達成APIなど）は、フロントから送られてきた申告ではなく、必ずこの関数の戻り値を使って実際に付与するポイント数を決めます。
- 対応する予定が見つからなければ`None`を返し、呼び出し側はこれを「そもそも存在しない課題ID」（＝改ざんされた/削除済みの課題）として扱い、処理を拒否できます。

```python
def _normalize_task_entry(entry):
    """旧形式（文字列）・旧dict形式（points/nicknameなし）・新形式を統一する"""
    if isinstance(entry, str):
        return {"id": entry, "date": None, "points": None, "nickname": None}
    entry = dict(entry)
    if "points" not in entry:
        entry["points"] = None
    if "nickname" not in entry:
        entry["nickname"] = None
    return entry
```
- 過去のバージョンの`completed_tasks_{guild_id}.json`には、機能追加のたびにデータの形式が変わってきた歴史があります（最初は課題IDの文字列だけの配列だった、次に辞書になったがポイントやニックネームのフィールドが無かった、など）。この関数は、どの世代の形式で保存されたデータが来ても、常に同じ形（`{"id", "date", "points", "nickname"}`を持つ辞書）に揃えるための「後方互換の橋渡し役」です。`isinstance(entry, str)`で文字列のままの古いデータかどうかを判定し、そうでなければ辞書として扱い、無いフィールドだけを`None`で補います。

def save_users(guild_id: int, users: list):

```python
def _users_text(users):
    """運用ログ用：users_{guild_id}.json を { ... } のブロックの並びにする。
    ★ 学籍番号・ニックネーム以外（Discord ID等）は含めない。"""
    lines = []
    for u in (users or []):
        lines.extend(_json_block([("学籍番号", u.get('id')), ("ニックネーム", u.get('nickname'))]))
    return "\n".join(lines)
```
- 運用ログ用の整形関数です。コメントで強調されている通り、**学籍番号・ニックネーム以外の情報（Discord IDなど、より個人を強く特定できる情報）は意図的に含めていません**。これは[../02_データ保存基盤/01_運用ログとdiff表示.md](../02_データ保存基盤/01_運用ログとdiff表示.md)で解説した、運用ログの設計方針（記録してよい情報の基準）を、このユーザーデータについて具体的に実践している箇所です。

```python
def find_user(guild_id: int, student_id: str):
    users = load_users(guild_id)
    return next((u for u in users if u.get("id") == student_id), None)
```
- 学籍番号（`student_id`）から、対応するユーザーのデータ（1件の辞書）を探します。`next((... for ... if ...), None)`は、「条件に合う最初の1件を探し、無ければ`None`を返す」というPythonのイディオム（定型的な書き方）です。この関数は、[00_ポイント課題達成ユーザーデータとレート制限.md](00_ポイント課題達成ユーザーデータとレート制限.md)の中でも後述する`require_login_json`をはじめ、「クライアントの自己申告ではなく、サーバー側の記録から本当のニックネームを引き直す」という場面で、このファイル全体を通して非常に頻繁に使われます。

## 4. 簡易レート制限（1124〜1157行）

コメントにある通り、これは総当たり攻撃（ブルートフォース攻撃。パスワードや確認コードを片っ端から試す攻撃）への対策です。ログインや、6桁（100万通り）の確認コードのような、繰り返し試行されやすいエンドポイント向けに使われます。外部のライブラリ（RedisなどのDBサーバー）を新たに導入せず、**Pythonのプロセス内メモリだけで完結する簡易な実装**です。コメントに明記されている通り、複数プロセスや複数台のサーバーで動かす場合はこの方式では効かなくなる（プロセスごとにメモリが別なので、試行回数が分散されて数えられてしまう）という制約がありますが、この用途（単一プロセスでの小規模運用）には十分と判断されています。

```python
_rate_limit_hits = {}  # "{bucket}:{ip}" -> [試行時刻, ...]
RATE_LIMIT_WINDOW_SEC = 15 * 60  # 15分
RATE_LIMIT_MAX_HITS = 10         # この回数を超えたら一時的に拒否

def _client_ip() -> str:
    xff = request.headers.get("X-Forwarded-For", "")
    if xff:
        return xff.split(",")[0].strip()
    return request.remote_addr or "unknown"
```
- `_rate_limit_hits`… `"バケット名:IPアドレス"`をキーとして、試行時刻のリストを保持するだけの、プロセスが生きている間だけ有効なメモリ上の辞書です。「バケット」とは、レート制限をかける対象（例えば「ログイン試行」「確認コード検証」）ごとの区分けのことです。
- `_client_ip()`… リクエスト元の実際のIPアドレスを取得します。`X-Forwarded-For`ヘッダーは、リバースプロキシ（サーバーの手前で通信を中継する仕組み）を経由している場合に、元々のクライアントの実IPアドレスを伝えるためのヘッダーです。これが無ければ、Flaskが直接受け取った接続元のアドレス（`request.remote_addr`）を使います。

```python
def rate_limited(bucket: str) -> bool:
    key = f"{bucket}:{_client_ip()}"
    now = time.time()
    hits = _rate_limit_hits.setdefault(key, [])
    hits[:] = [t for t in hits if now - t < RATE_LIMIT_WINDOW_SEC]
    if len(hits) >= RATE_LIMIT_MAX_HITS:
        return True
    hits.append(now)
    return False
```
- `bucket`ごと・IPアドレスごとに、直近15分間（`RATE_LIMIT_WINDOW_SEC`）の試行回数を数えます。
- `hits[:] = [t for t in hits if now - t < RATE_LIMIT_WINDOW_SEC]`… 15分より古い試行記録を、リストから間引きます（`hits[:] = ...`という書き方は、`hits`という同じリストオブジェクトの中身を書き換える、という意味です。単に`hits = [...]`と書いてしまうと、`_rate_limit_hits`辞書の中の値とは別の新しいリストを指すようになってしまい、辞書側には反映されません）。
- 直近の試行回数が`RATE_LIMIT_MAX_HITS`（10回）以上あれば`True`（拒否すべき）を返します。そうでなければ、今回の試行も記録に加えた上で`False`（許可）を返します。呼び出し側は、実際の処理（パスワード確認など）を行う**前**にこの関数を呼び、`True`なら処理自体を実行せずに拒否します。

```python
def rate_limit_response():
    return jsonify({"ok": False, "error": "too_many_attempts", "retry_after_sec": RATE_LIMIT_WINDOW_SEC}), 429
```
- レート制限に引っかかったときに返す、決まったエラーレスポンスです。`429`はHTTPのステータスコードで、「Too Many Requests（リクエストが多すぎる）」を意味する標準的な番号です。
