## 1. DM送信の共通処理：`send_discord_dm`（3425〜3449行）

```python
def send_discord_dm(guild_id: int, student_id: str, title: str, message: str):
    """
    ・連携していない場合は ValueError("not_linked") を送出する。
    ・★ 追加（2026/08/20）：対象サーバーのメンバーではない場合も同じ
      ValueError("not_linked") を送出する（＝制限付きアカウントには
      DM機能を一切使わせない方針。呼び出し側は元々「連携していない」
      場合のフォールバック処理を持っているため、そのまま流用できる）。
    ・送信自体に失敗した場合はその例外をそのまま送出する。
    """
    links = load_discord_links(guild_id)
    discord_user_id = links.get(str(student_id).strip().upper())
    if not discord_user_id:
        raise ValueError("not_linked")
    if _guild_membership_status(guild_id, int(discord_user_id)) != "member":
        raise ValueError("not_linked")

    async def _send():
        user = bot.get_user(int(discord_user_id))
        if user is None:
            user = await bot.fetch_user(int(discord_user_id))
        await user.send(f"**{title}**\n{message}")

    future = asyncio.run_coroutine_threadsafe(_send(), bot.loop)
    future.result(timeout=10)
```
- これが、これまでの回で何度も名前が登場していた、**DM送信の唯一の窓口**です。[[../04_勉強タイマー/00_勉強タイマーの状態管理.md]]の`_try_notify_timer`、[[../07_Discordコマンド/03_id連携とhelpコマンド.md]]の確認DM、[[01_OAuthコールバックと初回登録.md]]の連携完了DMなど、Bot からのDM送信は全てこの関数を経由します。
- コメントの通り、**同じ`ValueError("not_linked")`という例外が、実は2つの異なる理由（連携していない／メンバーではない）から発生しうる**という設計になっている点が興味深いところです。あえて理由を分けずに1つの例外に統一しているのは、コメントにある通り「呼び出し側は元々『連携していない』場合のフォールバック処理を持っているため、そのまま流用できる」という理由です。制限付きアカウントに対しては、新しく専用のエラーハンドリングを追加する必要が無く、既存の「未連携」の処理パスにそのまま乗せられるという、変更を小さく抑えるための実用的な判断です。
- `bot.get_user(...)`（キャッシュから取得。無ければ`None`）→`bot.fetch_user(...)`（キャッシュに無ければ、改めてDiscordのAPIに問い合わせて取得）という2段構えになっています。これは、頻繁に使うキャッシュを優先しつつ、キャッシュに無い場合でも確実にユーザーを取得できるようにするパターンです。
- `asyncio.run_coroutine_threadsafe(_send(), bot.loop)`… [[../09_FlaskAPI_予定管理/00_チャンネル一覧と予定の追加API.md]]の`add_schedule`で見たのと同じ、Flask（同期）からDiscord Bot（非同期のイベントループ）へ処理を依頼する橋渡しです。この`send_discord_dm`自体は普通の同期関数なので、内部で非同期関数`_send`をその場で定義し、`run_coroutine_threadsafe`経由で実行しています。

## 2. 新規ログイン通知：`_notify_new_login`（3452〜3472行）

```python
def _notify_new_login(guild_id: int, student_id: str, nickname: str):
    """
    ・「新たなログイン」とは、この関数の呼び出し＝create_session()の呼び出し
      そのものを指す。サイト内のページ遷移や再読み込みでは呼ばれない
      （ブラウザ側はlocalStorageの既存session_tokenを使い回すだけで、
      サーバーに新しいセッションを要求しないため）。
    ・対象サーバーのメンバーでなければ send_discord_dm() 側で自動的に
      スキップされる（制限付きアカウントにはDM機能自体を使わせない方針）。
    """
    try:
        send_discord_dm(
            guild_id, student_id,
            "新しいログインを検出しました",
            f"{nickname}（{student_id}）としてログインが行われました。\n"
            "心当たりが無い場合は、すぐに管理者に連絡してください。",
        )
    except Exception:
        pass
```
- これは、[[01_OAuthコールバックと初回登録.md]]で見た`_handle_discord_login_callback`と`discord_complete_registration`から呼ばれていた通知です。**セキュリティ通知としての役割**を持っています。もし誰かが自分の学籍番号を使って勝手にログインした場合、本人にすぐDMが届くため、不正なログインに気づきやすくなります。
- `except Exception: pass`… ベストエフォートな通知なので、送信失敗（未連携等）を理由にログイン処理自体を失敗させることはありません。

## 3. `/notify_dm`：Web側からのDM送信API（3475〜3508行）

```python
@app.route("/notify_dm", methods=["POST"])
def notify_dm():
    data    = request.json or {}
    guild_id = data.get("guild_id")
    title   = data.get("title") or "StudyLog"
    message = data.get("message")

    if not all([guild_id, message]):
        return jsonify({"ok": False, "error": "missing fields"})

    guild_id   = int(guild_id)
    student_id, err = require_member_session(data.get("session_token"), guild_id)
    if err:
        return err

    try:
        send_discord_dm(guild_id, student_id, title, message)
        return jsonify({"ok": True})
    except ValueError:
        return jsonify({"ok": False, "error": "not_linked"})
    except Exception as e:
        return jsonify({"ok": False, "error": f"dm_failed: {e}"})
```
- コメントの通り、**本人確認が重要な理由**は「他人の`student_id`を指定して勝手にDMを送りつけられないようにする」ためです。`require_member_session`で本人確認をし、送り先はあくまで`data.get("student_id")`のような自己申告ではなく、**セッションから特定した本人自身**（＝自分自身にしかDMを送れない）になっています。このAPIは「自分にリマインダーを送る」ような用途（例えばタイマーの通知）で使われる想定です。
- `except ValueError:`で`send_discord_dm`からの`"not_linked"`エラーを受け取り、専用のエラーコードとしてそのままフロントへ伝えます。コメントの通り、フロント側はこれを見て「DM機能の代わりにブラウザ通知にフォールバックする」といった動作ができます。

## 4. 問題報告フォーム：`/report_problem`（3511〜3559行）

```python
def _report_problem_result_page(success: bool, message: str) -> str:
    ...
    <div style="...">{html.escape(message)}</div>
    ...
```
- [[01_OAuthコールバックと初回登録.md]]の`_oauth_result_page`と似た、結果表示用の簡易HTMLです。**ただし決定的な違いがあります**：`{html.escape(message)}`で、埋め込む`message`をエスケープしています。`_oauth_result_page`のメッセージがサーバー側が用意した固定文言だけだったのに対し、こちらの`message`は**利用者が入力したテキストに由来する**可能性があるためです（後述）。`html.escape`は、`<`や`&`のようなHTML上で特別な意味を持つ文字を、`&lt;`のような無害な表記に変換する、標準ライブラリの関数です。これにより、利用者が`<script>...</script>`のような文字列を報告メッセージに入力しても、それがそのままHTMLとして解釈されてスクリプトとして実行されてしまう事態（XSS）を防いでいます。

```python
@app.route("/report_problem", methods=["POST"])
def report_problem():
    """
    ★ 2026/08/19 追加：サイトのJSが完全に動かなくなった場合でも必ず表示される
      「読み込み中…」の代替表示（各ページの<body>の一番先頭に生HTMLで
      埋め込んである。各ページのJSが最後まで正常に初期化できたときだけ
      非表示にする＝JSが途中で止まっていれば表示され続ける）から送られる、
      普通の<form method="POST">（fetchではない）。JSが完全に死んでいても
      ブラウザの標準機能だけで送信できることが目的。
      ログイン中かどうかも問わない（JSが動かない前提のため、localStorageの
      セッション情報を読み出せるとは限らない）＝匿名の報告として扱う。
    """
    guild_id_raw = request.form.get("guild_id")
    page    = (request.form.get("page") or "不明なページ").strip()[:80]
    message = (request.form.get("message") or "").strip()[:500]
```
- コメントの背景が興味深いところです。もしページのJavaScriptが致命的なバグで完全に止まってしまったら、そもそも`fetch()`によるAPI呼び出しすら実行できません。そこで、各ページの`<body>`の先頭にあらかじめ**生のHTMLとして**（JavaScriptに一切頼らない）「読み込み中…」の代替表示と、その中に埋め込まれた**普通のHTMLフォーム**（`<form method="POST">`。JavaScriptが一切動かなくても、ブラウザ標準の機能だけでサーバーに送信できる、昔ながらのやり方）を用意しておき、これがその送信先です。
- `request.form.get(...)`… これまでの`request.json`（JavaScriptの`fetch`がJSON形式で送るデータ）とは違い、通常のHTMLフォームが送信するデータ形式（`application/x-www-form-urlencoded`）を読み取る場合はこちらを使います。
- コメントの通り、ログイン中かどうかを問わない**匿名の報告**として扱われます。これは、JSが動かない前提である以上、`localStorage`に保存されているはずのセッション情報すら読み出して送信できるとは限らないためです。

```python
    try:
        guild_id = int(guild_id_raw)
    except (TypeError, ValueError):
        return _report_problem_result_page(False, "不正なリクエストです。")

    body = f"ページ: {page}\n" + (f"内容: {message}" if message else "（内容の記入なし）")
    body += "\n※JSが動かない状態からの送信のため、送信者は匿名です。"

    try:
        send_discord_dm(guild_id, REPORT_PROBLEM_ADMIN_STUDENT_ID, "サイトの問題報告", body)
        return _report_problem_result_page(True, "報告を送信しました。ありがとうございます。")
    except ValueError:
        return _report_problem_result_page(False, "管理者への送信に失敗しました（Discord未連携）。直接Discordで連絡してください。")
    except Exception:
        return _report_problem_result_page(False, "送信に失敗しました。時間を置いてもう一度お試しください。")
```
- `page`・`message`は、それぞれ`[:80]`・`[:500]`で文字数を強制的に制限してから使います（利用者が入力した任意の長さのテキストを、無制限にDiscordへ転送しないための安全弁です）。
- [[../01_起動と初期設定/00_設定の読み込みとFlask_Discordの初期化.md]]で見た`REPORT_PROBLEM_ADMIN_STUDENT_ID`（緊急連絡先の学籍番号）宛に、`send_discord_dm`でDMを送ります。ログインしていない匿名の利用者からの報告であっても、送信先は固定の管理者アカウントなので、[[../05_ユーザーとセッション]]で見たようなログイン確認は不要です（このAPI自体が「誰が送ったか分からない」ことを前提にしているため、あくまで送信先を固定管理者に限定することが安全性の担保になっています）。
- ここでも不正文字チェック（`reject_if_bug_chars`）は行われていない点に気づいたかもしれません。これは、`page`/`message`の送信先が**画面上に表示されるWebページの一部としてではなく、Discordのメッセージとして**送られるためです（Discordメッセージ自体は不可視文字が含まれていても、[[../02_データ保存基盤/02_設定ファイルと不正文字チェック.md]]で懸念されていたようなデータ破損やコミット差分の表示崩れを引き起こしません）。ただし前述の通り、`_report_problem_result_page`側で改めて`html.escape`しているのは、結果画面に表示し返す際にHTMLとして解釈されないようにするための、別の観点の対策です。
