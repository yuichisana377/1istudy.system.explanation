# 削除依頼トークンと `/request_delete`（`bot.py` 3562〜3764行）

対象：`bot.py`の「削除の作成者確認（カードデッキ／お知らせ）」セクション前半。[../../1I勉強会web解説/10_DeleteApproval/00_DeleteApproval解説.md](../../1I勉強会web解説/10_DeleteApproval/00_DeleteApproval解説.md)で見た「削除の確認ページ」の、**サーバー側の実装**がここにあります。

## 背景と設計方針（コメントより）

カードデッキ（`words/*.json`）・お知らせ（`notices/*`）は、以前は作成者本人以外の誰でも削除できてしまい、作成者が知らないうちに自分の作ったものが消えることがありました。ここで実装されているのは、「本人以外は直接削除できないようにし、削除したい場合は理由付きで作成者にDiscord DMを送って承認/拒否してもらう」というフローです。

設計上の要点は次の通りです。
- 作成者チェック本体（本当に本人かどうかの判定）は、後の章で見る`_delete_cards`/`_delete_notice`側（それぞれ`_deck_owner`/`_notice_owner`を使用）に入っています。ここにあるのは「作成者以外からの削除依頼」を**仲介する部分だけ**です。
- 依頼〜承認はDBを持たず、[../05_ユーザーとセッション/01_セッショントークンと権限チェック.md](../05_ユーザーとセッション/01_セッショントークンと権限チェック.md)の`create_session`と同じ「署名付きトークンに必要な情報を全部載せる」方式（**ステートレス**＝サーバーが状態を覚えておかなくてよい）にしてあります。SESSION_SECRETまわりで見たのと同じ考え方で、トークン失効リストのような仕組みまで持つのはこのアプリの規模ではオーバーエンジニアと判断されています。
  - トークンは14日間で自然に失効します。
  - 承認/拒否はDMのリンクを開くだけで完了します（本人のDiscordにしか届かない前提で、あえてログインを要求していません）。
  - 同じリンクを2回押す（例：承認後にもう一度承認）といった操作は「その時点の実ファイルに対してもう一度実行する」だけなので、既に消えていれば「ファイルが見つかりません」を返して実害は無いという扱いです（＝厳密な二重実行防止は持ちません）。
- 作成者がDiscord未連携（`/id連携`未実施）の場合は依頼を送れません（＝安全側に倒して削除をブロックしたままにします。連携すれば解決します）。
- 作成者が記録されていない古いデッキ／お知らせ（この機能の導入前に公開されたもの）は、従来通り誰でも直接削除できます（`_deck_owner`/`_notice_owner`が`(None, None)`を返すため）。

## 1. 署名付きトークン（3593〜3619行）

```python
DELETE_APPROVAL_URL = "https://1istudyweb.pages.dev/DeleteApproval.html"
DELETE_REQUEST_TOKEN_TTL_SEC = 60 * 60 * 24 * 14  # 14日間有効

def create_delete_request_token(payload: dict) -> str:
    body = dict(payload)
    body["_t"] = int(time.time())
    payload_json = json.dumps(body, ensure_ascii=False, separators=(",", ":"))
    payload_b64 = base64.urlsafe_b64encode(payload_json.encode()).decode()
    sig = hmac.new(SESSION_SECRET.encode(), payload_b64.encode(), hashlib.sha256).hexdigest()
    return f"{payload_b64}.{sig}"

def resolve_delete_request_token(token: str):
    if not token or "." not in token:
        return None
    try:
        payload_b64, sig = token.rsplit(".", 1)
        expected_sig = hmac.new(SESSION_SECRET.encode(), payload_b64.encode(), hashlib.sha256).hexdigest()
        if not hmac.compare_digest(sig, expected_sig):
            return None
        payload = json.loads(base64.urlsafe_b64decode(payload_b64.encode()).decode())
        if time.time() - payload.get("_t", 0) > DELETE_REQUEST_TOKEN_TTL_SEC:
            return None
        return payload
    except Exception:
        return None
```
- 作りは[../05_ユーザーとセッション/01_セッショントークンと権限チェック.md](../05_ユーザーとセッション/01_セッショントークンと権限チェック.md)の`create_session`/`resolve_session`と全く同じ「HMAC署名付きトークン」パターンです。違いは、埋め込む中身が`guild_id`と`student_id`だけではなく、**削除依頼に必要な情報全部**（誰が・何を・なぜ削除したいか）である点です。トークン自体が「依頼内容そのものを封筒に入れて持ち運んでいる」ようなイメージです。サーバー側は依頼を保存しておく必要が無く、DMに書かれたリンクのトークンさえ読み解ければ、依頼の全内容を復元できます。
- `SESSION_SECRET`（ログインセッションと同じ秘密鍵）を流用している点にも注目してください。同じ鍵を使い回すことで、新しい秘密鍵を追加で管理する手間を避けています（ただし、後述の通りこのトークンには`purpose`のような「トークンの種類」を区別するフィールドが無いため、理論上は他の署名付きトークンと構造が混同されないよう、それぞれの`resolve_*`関数が期待するフィールド（`_t`と、実際に使われるキー）が異なることで暗に区別されています）。

## 2. Web確認待ちの控え（3621〜3630行）

```python
def load_pending_delete_requests(guild_id):
    """Discord未連携のためDMを送れなかった削除依頼の控え（Web確認待ち）。"""
    data, sha = local_get(f"pending_delete_requests_{guild_id}.json")
    return (data or []), sha

def save_pending_delete_requests(guild_id, items, sha=None):
    if sha is None:
        _, sha = local_get(f"pending_delete_requests_{guild_id}.json")
    local_put(f"pending_delete_requests_{guild_id}.json", items, sha)
```

## 3. 削除対象の表示情報：`_delete_target_summary`（3632〜3663行）

```python
def _delete_target_summary(category, filename):
    """「今まさに削除されようとしている中身」を人が読める形にする。
    (表示名, 詳細行のリスト) を返す。読めない場合は (filename, [])。
    ★ 承認ページはリンクを開いた時点の最新の中身を都度取得して表示する
    （依頼を送った時点のスナップショットではない＝実際に消える中身と一致する）。"""
    if category == "deck":
        data, _ = get_card_file(filename)
        if not data:
            return filename, []
        name = data.get("name") or filename
        cards = data.get("cards") or []
        lines = [
            f"科目: {data.get('subject') or '（なし）'}",
            f"問題数: {len(cards)}問",
            "状態: " + ("未完成（作成中）" if data.get("incomplete") else "完成"),
        ]
        preview = [f"・{(c.get('question') or '').strip()[:60]}" for c in cards[:5] if (c.get("question") or "").strip()]
        if preview:
            lines.append("--- 内容（先頭" + str(len(preview)) + "問の問題文） ---")
            lines.extend(preview)
        return name, lines
    elif category == "notice":
        path = _data_path(f"{NOTICES_DIR}/{filename}")
        content = None
        if os.path.isfile(path):
            try:
                with open(path, "r", encoding="utf-8") as f:
                    content = f.read()
            except OSError:
                content = None
        return filename, [content if content is not None else "（内容を読み込めませんでした）"]
    return filename, []
```
- コメントが設計の要点を明確に示しています。この関数は、依頼を送った時点の内容（スナップショット）を保存しておくのではなく、**呼ばれるたびに、その時点での最新の実ファイルを読みに行きます**。これにより、削除承認ページ（[../../1I勉強会web解説/10_DeleteApproval/00_DeleteApproval解説.md](../../1I勉強会web解説/10_DeleteApproval/00_DeleteApproval解説.md)）を開いたときに表示される内容が、依頼された後にさらに編集されていても、常に「実際に今消えようとしている中身」と完全に一致します。もし依頼時点の内容を固定して保存していたら、「見た内容と、実際に削除される内容が食い違う」という事故が起こりえます。
- `category`によって扱いが分かれます。デッキなら`get_card_file`（後の章で解説）でカードデータを取得し、科目・問題数・状態（未完成/完成）に加え、先頭5問の問題文のプレビューを組み立てます。お知らせなら、単純にファイルの中身をテキストとして読み込みます。

## 4. `/request_delete`：削除依頼の送信（3665〜3764行）

```python
@app.route("/request_delete", methods=["POST"])
def request_delete():
    data = request.json or {}
    guild_id, requester_id, requester_nickname, err = require_login_json(data)
    if err:
        return err
    category = data.get("category")
    filename = data.get("filename")
    reason = (data.get("reason") or "").strip()
    if category not in ("deck", "notice"):
        return jsonify({"ok": False, "error": "invalid category"})
    if not filename:
        return jsonify({"ok": False, "error": "filename は必須です"})
    if not reason:
        return jsonify({"ok": False, "error": "理由を入力してください"})
    if len(reason) > 500:
        return jsonify({"ok": False, "error": "理由は500文字以内で入力してください"})
    err = reject_if_bug_chars({"削除理由": reason})
    if err:
        return err
```
- `category not in ("deck", "notice")`… `category`は「カードデッキ」か「お知らせ」のどちらかのみ許可されるという、いわゆるホワイトリスト方式の検証です。それ以外の値を無条件に拒否します。
- 削除理由（`reason`）は必須・500文字以内・不正文字チェック済みという、しっかりとしたバリデーションが行われています。これは他人に送られるDMメッセージに直接含まれる文字列なので、特に丁寧に検証されています。

```python
    if category == "deck":
        if "/" in filename or "\\" in filename or ".." in filename:
            return jsonify({"ok": False, "error": "invalid filename"})
        owner_id, owner_nickname = _deck_owner(filename)
    else:
        if not _is_safe_notice_filename(filename):
            return jsonify({"ok": False, "error": "invalid filename"})

    if str(owner_id) == str(requester_id):
        return jsonify({"ok": False, "error": "本人はこの手続きを使わず直接削除できます。"})
```
- `"/" in filename or "\\" in filename or ".." in filename`… これは**パストラバーサル対策**です。`filename`は本来「サーバー内のこのデータフォルダにある1つのファイルの名前」であるべきですが、もし`"../../etc/passwd"`のような文字列がそのままファイルパスの組み立てに使われてしまうと、意図しない別の場所にあるファイルを読み書きされてしまう危険があります。スラッシュ・バックスラッシュ・`..`（親ディレクトリへ移動する記法）を禁止することで、渡された`filename`が必ず「単純な1つのファイル名」だけになるよう強制しています。
- `owner_id`が取得できない（作成者情報が記録されていない古いデータ）場合は、コメント通り「安全側に倒して削除をブロックしたまま」にします。
- `owner_id == requester_id`（依頼者が実は作成者本人だった）場合は、そもそもこの依頼という手続き自体が不要（本人なら直接削除できる）なので、エラーとして案内します。

- **ここに、コメントで説明されている設計変更の経緯があります**。以前は、DMが送れない理由が「未連携（`ValueError`）」の場合だけこのフォールバック（後述の`pending_delete_requests`への控え）に乗せ、それ以外の例外（DM拒否設定やDiscordの一時的な通信エラーなど）は`dm_failed`として依頼自体を失敗させていました。しかしそれでは、「DMは失敗したのに、通知が一切残らない」という事故（作成者にはDMも届かず、Web上にも記録が残らず、削除依頼自体が宙に浮いてしまう）につながることが分かり、**理由を問わず全ての送信失敗で同じフォールバックに乗せる**方針に変更されています（`except Exception as e:`で、`send_discord_dm`が投げうるあらゆる例外を一括で捕まえています）。
- フォールバック先は`pending_delete_requests_{guild_id}.json`への控えです。ここに依頼を保存しておき、作成者が次にWebサイトのいずれかのページを開いたときに（`PendingDeleteCheck.js`。フロント側の共通コンポーネントとして紹介済みです）確認モーダルが出るようにします。DMという「プッシュ型」の通知が失敗しても、Webサイトを開いたときの「プル型」の確認で必ず拾えるようにする、二段構えの設計です。
- `notified_via`（`"discord_dm"`か`"web_pending"`）をレスポンスに含めることで、フロント側は「DMを送りました」「DMが送れなかったので、作成者が次にサイトを開いたときに表示されます」のように、実際に起きたことを利用者に正しく伝えられます。
