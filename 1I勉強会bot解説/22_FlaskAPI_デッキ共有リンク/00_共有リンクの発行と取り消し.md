# CardMakerの共有リンク：発行の仕組み（`bot.py` 4805〜5116行）

対象：`bot.py`の「CardMaker — 未ログインの人にも見せられる『共有リンク』（デッキ単位・閲覧専用）」セクション前半。Web側の実装（`Cardmaker.js`のメニュー追加・`DeckShare.html`）は[../../1I勉強会web解説/12_DeckShare/00_解説.md](../../1I勉強会web解説/12_DeckShare/00_解説.md)を参照。

## 背景と設計方針（コメントより）

CardMakerのデッキは元々ログイン必須のページの中でしか見られません。「どうしても見せたい相手（サーバー未参加・未ログイン）」にだけ、特定の1デッキを閲覧専用で見せたい、という要望から追加されたのがこの機能です。

方針は次の通りです（すべてユーザーの明示的な指定）。
- 見せるのは指定した1デッキの中身だけ。予定・時間割・他のデッキ等、サイトの他の部分は一切見せません（専用の閲覧ページ`DeckShare.html`を別途用意し、ドロワー等のナビゲーションを持たせません）。
- 共有された側（リンクを受け取って開くだけの人）に変更権は一切与えません（閲覧専用のAPIしか用意していません）。
- 共有リンクを作れるのは、サーバー参加済みのログインユーザーのみ。ただし**直接発行できるのはそのデッキの作成者本人だけ**で、本人以外が共有したい場合は作成者へDiscordで確認を送り、承認されて初めて「1回分の権利（グラント）」が得られます（[../12_FlaskAPI_削除依頼システム/00_削除依頼トークンと送信フロー.md](../12_FlaskAPI_削除依頼システム/00_削除依頼トークンと送信フロー.md)で見た`delete_cards`の`creator_approval_required`／`request_delete`と同じ考え方の、共有版だと思ってください）。
  - **承認しても、その場で共有リンクそのものが自動発行されるわけではありません**。依頼者が改めてCardMaker側で「共有リンクを作る」を押した時点で、権利が1件消費されて初めて発行されます。これは、グラントを渡す経路（Discord DM）の到達を必須にしないための設計です。DMが失敗しても、依頼者はいつでも自分でボタンを押し直せば発行できます。
- 1人が1日に作成できる共有リンクは3件まで（本人が直接作成した分・グラントを消費して作成した分の合計。JST基準の日付で判定）。
- 共有リンクの有効期限は30日間（「本当に見せたい相手に渡すためのものなので、長くはいらない。長く必要ならサーバーに入ってもらう想定」というユーザーの考え方）。作成者・共有した本人はいつでも取り消せます。
- `deck_shares_{guild_id}.json`には、ページ本体には出さない秘密のtoken（＝合言葉そのもの）が入っています。このため、[../02_データ保存基盤/01_運用ログとdiff表示.md](../02_データ保存基盤/01_運用ログとdiff表示.md)で見た運用ログ（`system_log`、ログイン不要で閲覧可能）には**このファイルの中身を絶対に出しません**（他カテゴリのような`file_diff`方式をあえて使わず、tokenを含まない要約テキストだけを`log_event`に渡しています）。

- 共有リンクのtoken（`DeckShare.html?token=...`のクエリに載る文字列）は、`secrets.token_urlsafe(24)`（24バイト＝192ビットのランダム値）の**先頭にguild_idをそのまま平文で付け足しただけ**のシンプルな形です。`guild_id`自体は秘密情報ではない（このアプリは実質1サーバー運用）ので隠す意味が無く、逆にguild_idを埋め込んでおくことで、あとで見る`deck_share_info`（閲覧API）が「どのguildの`deck_shares_{guild_id}.json`を見に行けばいいか」をtoken自体から判定できるようになっています（＝毎回全guildのファイルを総当たりで探さなくて済みます）。
- 一方、削除確認依頼（[12_FlaskAPI_削除依頼システム](../12_FlaskAPI_削除依頼システム/00_削除依頼トークンと送信フロー.md)）のトークンは「HMAC署名付きの封筒に情報を全部詰め込む」ステートレス方式でした。共有リンクの`token`はそれとは違い、**ランダムな合言葉をサーバー側のファイル（`deck_shares_{guild_id}.json`）に保存しておくステートフルな方式**です。理由は、この機能には「1日3件までの上限」「取り消し（無効化）」という、状態を覚えておかないと実現できない要件があるためです（ステートレスな署名トークンだと、発行した数を数えたり、あとから個別に無効化したりできません）。

## 2. 共有リンク本体のストレージ（4887〜4944行）

```python
def load_deck_shares(guild_id):
    data, sha = local_get(f"deck_shares_{guild_id}.json")
    return (data or []), sha

def save_deck_shares(guild_id, items, sha=None):
    now = time.time()
    items[:] = [it for it in items if now - it.get("created_at", 0) <= DECK_SHARE_KEEP_SEC]
    if sha is None:
        _, sha = local_get(f"deck_shares_{guild_id}.json")
    local_put(f"deck_shares_{guild_id}.json", items, sha)
```
- `save_deck_shares`は保存の直前に**古いエントリの掃除**を行います。`DECK_SHARE_KEEP_SEC`（35日）は、有効期限の30日より少し長めに設定してあります。これは、期限が切れた直後のエントリも「今日の3件」の集計対象からすぐには外さない（＝下の`_deck_share_count_today`が正しく機能する期間には残しておく）ための余裕です。`SYSTEM_LOG_MAX_ENTRIES`（[02_データ保存基盤](../02_データ保存基盤/01_運用ログとdiff表示.md)参照）の「件数」で切り捨てる方式とは違い、こちらは「経過時間」で切り捨てる方式です。

```python
def _deck_share_count_today(items, student_id):
    """本日（JST）、この人が作成した（＝自分の1日3件の枠を使った）共有の件数。
    取り消し済みでも「その日に作った」事実は変わらないため上限判定には含める
    （でないと 作成→取り消し→作成 を繰り返して上限を回避できてしまう）。"""
    today = datetime.now(JST).date()
    count = 0
    for it in items:
        if str(it.get("created_by")) != str(student_id):
            continue
        created = datetime.fromtimestamp(it.get("created_at", 0), JST).date()
        if created == today:
            count += 1
    return count
```
- コメントにある通りがポイントです。「取り消し済みかどうか」を見ずに、「今日作った件数」だけを数えます。もし取り消し済みのエントリを除外して数えていたら、「作成→即取り消し→また作成」を繰り返すことで1日3件の上限を無限に回避できてしまいます（＝取り消しは「見せる相手を減らす」ためのものであって、「発行した回数を無かったことにする」ものではない、という設計）。

```python
def _create_deck_share_entry(items, guild_id, filename, deck_name, student_id, nickname, via_request, approved_by_nickname):
    now = int(time.time())
    entry = {
        "token": _new_share_token(guild_id),
        "filename": filename,
        "deck_name": deck_name,
        "created_by": student_id,
        "created_by_nickname": nickname,
        "created_at": now,
        "expires_at": now + DECK_SHARE_TTL_SEC,
        "via_request": via_request,
        "approved_by_nickname": approved_by_nickname,
        "revoked_at": None,
    }
    items.append(entry)
    return entry
```
- `deck_name`は、`filename`（内部識別子）とは別に**発行した時点のデッキ名をスナップショットとして保存**しています。これは、あとで運用ログ（`_deck_share_log_lines`）や共有リンク一覧（`list_deck_shares`）に「対象デッキ: ○○」と表示する際、毎回`get_card_file`でファイルを読みに行かなくても名前が分かるようにするためです（[12_FlaskAPI_削除依頼システム](../12_FlaskAPI_削除依頼システム/00_削除依頼トークンと送信フロー.md)の`_delete_target_summary`が「閲覧時点の最新の中身」をあえて毎回読みに行っていたのとは対照的です。削除確認は「今まさに消えるものと表示が食い違うと事故になる」ため常に最新を見る必要がありましたが、こちらの`deck_name`は単なる管理画面上のラベルなので、スナップショットで十分と判断されています）。

```python
def _deck_share_log_lines(entry):
    """★ deck_shares_{guild_id}.json自体はtoken（合言葉そのもの）を含むため、
    他カテゴリのようにfile_diff()でファイルの中身をそのまま運用ログ（ログイン
    不要で閲覧可能）に出すことは絶対にしない。ここで作る文字列にはtokenを
    含めず、デッキ名と有効期限だけを表示する。"""
    expires_str = datetime.fromtimestamp(entry["expires_at"], JST).strftime("%Y-%m-%d")
    return f"対象デッキ: {entry['deck_name']}\n有効期限: {expires_str}まで（30日間）"
```
- ここが**セキュリティ上、最も注意深く作られている部分**です。[02_データ保存基盤/01_運用ログとdiff表示.md](../02_データ保存基盤/01_運用ログとdiff表示.md)で見た通り、カードデッキ等の変更は普通`deck_file_diff()`のような「ファイルの中身をそのまま行差分にする」仕組みでログに残ります。しかし、もし`deck_shares_{guild_id}.json`に同じ仕組みを使うと、ファイルの中身に含まれる**秘密のtoken**が、ログイン不要で誰でも読める運用ログにそのまま出力されてしまいます（＝共有リンクの合言葉が誰にでも分かってしまい、閲覧専用リンクのはずが実質「全世界に公開」と同じ状態になる重大な事故です）。これを避けるため、この関数だけは`file_diff`系のヘルパーを一切使わず、**手作りの、tokenを含まない要約文字列**を組み立てています。

- 発行に成功した**後で**グラントの`used_at`を書き込む順序に注目してください。もし先にグラントを消費してから発行処理を行い、その途中で（例えば1日の上限に達していて）発行が失敗すると、「グラントだけ無駄に消費されて、リンクは発行されない」という事故になります。この順序（先に本体を作ってから、副作用としてグラントを消費する）で、その事故を避けています。

## 4. `/list_deck_shares`・`/revoke_deck_share`（5046〜5116行）


- CardMakerのデッキ編集画面に出す「共有中のリンク」一覧のためのAPIです。フィルタ条件に注目してください：**そのリンクを実際に作った本人**か、**そのデッキの作成者本人**のどちらかでなければ、一覧に出てきません。これにより、たとえば依頼者Aが承認を得て発行したリンクは、デッキ作成者Bの一覧にもAの一覧にも出てきますが、無関係な第三者Cには（Cがこのデッキの作成者でもリンクの発行者でもない限り）一切見えません。「他人が作った共有の存在自体を知られないようにする」という設計です。
- `remaining_today`（レスポンスの一部）も`_deck_share_count_today`で計算しており、CardMaker側の「本日あと◯件作成できます」という表示に使われます。
