# デッキの作成者確認と削除（`bot.py` 4592〜4669行）

対象：`bot.py`の`_deck_owner`・`_delete_card_deck_file`・`/delete_cards`。これで「Flask API — 単語カード」の章が終わります。[[../12_FlaskAPI_削除依頼システム]]で見た削除依頼システムが、実際にここで使われます。

## 1. 作成者の判定：`_deck_owner`（4592〜4602行）

```python
def _deck_owner(filename):
    """
    読めない／記録が無い（作成者確認機能より前に公開された古いデッキ等）
    場合は (None, None)。owner_id が None のときは「作成者不明」として
    従来通り誰でも削除できる扱いにする（過去のデッキを誰も削除できなくなる
    事態を避けるため）。"""
    data, _ = get_card_file(filename)
    if not data:
        return None, None
    pub = data.get("published_by") or {}
    return pub.get("id"), pub.get("nickname")
```
- これが、[[../12_FlaskAPI_削除依頼システム/00_削除依頼トークンと送信フロー.md]]で名前だけ登場していた関数の実体です。[[01_一覧取得と保存API.md]]で見た`/save_cards`が保存する`published_by.id`を読み出すだけの、シンプルな関数です。
- コメントの通り、この機能が導入される**前**に公開された古いデッキには、そもそも`published_by`という情報自体が記録されていません。その場合は`(None, None)`を返し、呼び出し側はこれを「作成者不明」として、従来通り誰でも削除できる扱いにします。これは「過去のデータを、新しい安全機能によって誰も触れなくしてしまう」という事態を避けるための、現実的な判断です。

## 2. 実際の削除処理：`_delete_card_deck_file`（4604〜4636行）

```python
def _delete_card_deck_file(filename, actor_nickname, approval_note=None):
    """デッキファイル削除の実処理（本人による直接削除・削除依頼の承認の
    どちらからも呼ばれる共通処理）。作成者チェックは呼び出し側の責務。"""
    path = _data_path(f"{CARDS_DIR}/{filename}")
    if not os.path.isfile(path):
        return jsonify({"ok": False, "error": "ファイルが見つかりません"})

    deleted_data, _ = get_card_file(filename)
    deleted_name = (deleted_data or {}).get("name")
    try:
        os.remove(path)
    except OSError as e:
        return jsonify({"ok": False, "error": f"local_delete_failed: {e}"})

    index_change = None
    try:
        index_change = remove_cards_index_entry(filename)
    except DataWriteError as e:
        print(f"[WARN] cards_index からの削除に失敗しました: {e}")

    cleanup_list_order(remove_keys={f"deck:{filename}"})

    change = deck_file_diff(f"{CARDS_DIR}/{filename}", deleted_data, None)
    detail = [c for c in (change, index_change) if c]
    summary = f"カードデッキ「{deleted_name}」を削除しました。" if deleted_name else "カードデッキを削除しました。"
    if approval_note:
        summary += approval_note
    log_event("card", summary, actor=actor_nickname, detail=detail if detail else None)
    return jsonify({"ok": True})
```
- コメントにある通り、この関数自体は**「作成者チェックは呼び出し側の責務」**であり、この関数自身は誰が呼んでも無条件で削除を実行します。これは意図的な設計で、この関数は2つの異なる入口（本人による直接削除、そして[[../12_FlaskAPI_削除依頼システム/01_承認ページのAPIと結果の反映.md]]で見た削除依頼の承認）から共通で呼ばれるため、認可のロジックをこの関数の**外側**（呼び出し元）に集約することで、削除の実処理自体は「どこから呼ばれても同じことをする」というシンプルさを保っています。
- `deleted_data, _ = get_card_file(filename)`… ファイルを実際に削除する**前**に、中身を読んでおきます。コメントの通り、これは運用ログの表示用です。「もし読めなかった場合はデッキ名・カードの内容が分からないので、無理に内部ファイル名（ハッシュ）などを代わりに出さず、それらの表示自体を省く」という方針で、`deleted_name`が`None`なら、`summary`のメッセージも「カードデッキを削除しました」というだけの、名前無しの汎用的な文言になります（`if deleted_name else`の三項式）。
- `os.remove(path)`… ここで実際にファイルシステムからファイルが消えます。[[00_カードデータ層と索引管理.md]]の`upsert_cards_index_entry`（索引の更新）と同様に、索引からの削除・並び順からの削除も、それぞれ独立した`try`/`except`で囲まれており、これらの後処理の失敗が「ファイル自体は既に削除された」という主目的の結果を覆すことはありません。
- `cleanup_list_order(remove_keys={f"deck:{filename}"})`… カードの並び順を管理する`list_order.json`（後の章で解説）からも、このデッキのキーを取り除きます。存在しないデッキへの並び順情報が、いつまでも残り続けないようにするための後片付けです。
- `approval_note`… [[../12_FlaskAPI_削除依頼システム/01_承認ページのAPIと結果の反映.md]]で見た通り、削除依頼の承認経由で呼ばれた場合だけ、`summary`に「（〇〇さんの削除依頼を△△さんが承認）」という文脈が追記されます。

## 3. `/delete_cards`：削除の入口（4638〜4669行）

```python
@app.route("/delete_cards", methods=["POST"])
def delete_cards():
    data     = request.json
    _guild_id, _student_id, nickname, err = require_login_json(data)
    if err:
        return err
    filename = data.get("filename")
    if not filename:
        return jsonify({"ok": False, "error": "filename は必須です"})
    if "/" in filename or "\\" in filename or ".." in filename:
        return jsonify({"ok": False, "error": "invalid filename"})
```
- [[../12_FlaskAPI_削除依頼システム/00_削除依頼トークンと送信フロー.md]]の`/request_delete`と同じ、パストラバーサル対策のファイル名検証です。

- **これが認可ロジックの本体**です。`_deck_owner`で作成者を調べ、`owner_id`が存在していて、かつそれが今リクエストしている本人（`_student_id`）と違う場合は、実際には削除せず`"creator_approval_required"`という専用のエラーコードを返します。[[../../1I勉強会web解説/02_Cardmaker/03_Cardmaker.js_その3_デッキの読み込みと作成編集.md]]で見た通り、フロント側はこのエラーコードを見て、削除依頼（`/request_delete`）のモーダルへ誘導します。
- コメントには、**一度実装したものの元に戻された（revert）判断**が記録されているという、珍しく貴重な例です。一時期、「`discord_links`に紐づいていない生徒＝もう誰も使っていない孤立したアカウント」とみなし、そういうデッキについては確認フローを自動でスキップする（＝直接削除を許可する）という判定を入れていたことがありました。しかし、これは「まだ`/id連携`（DM通知用の紐付け）をしていないだけの、現役で活動中の本人」まで巻き込んでしまうことに気づき、**セキュリティ上の後退**だったとして元に戻されています。「DM連携がまだ無い＝もうそのアカウントは二度と使われない」とは言い切れない、という当たり前だが見落としやすい前提が、この判断の核心です。コメントの最後にある通り、「本当に誰にも確認できない孤立したデータ」への対応は、自動判定という一律のルールではなく、管理者による個別対応のような、より慎重な手段に委ねる方針に変わっています。
- `owner_id`が`None`（作成者不明の古いデッキ）の場合は、この`if`に引っかからず、そのまま`_delete_card_deck_file`が呼ばれて削除が実行されます（[[../12_FlaskAPI_削除依頼システム/00_削除依頼トークンと送信フロー.md]]で見た通り、これは意図的な仕様です）。
