## 1. `/delete_study_log`：学習ログの削除（2440〜2489行）

```python
@app.route("/delete_study_log", methods=["POST"])
def delete_study_log():
    """
    自分の勉強ログ1件を削除する（2026/08/19追加）。
    ・本人の記録以外は削除できない（student_idはセッションから特定、
      クライアント自己申告は信用しない）。
    ・記録済みのポイント（5分ごとに1pt）はその分だけ差し引く（0未満にはしない）。
    ・study_logs_{guild_id}.jsonは全生徒共有の1ファイルなので、ここから
      該当エントリを取り除くだけで「みんなの記録」からも自動的に消える
      （StudyLog.jsのrenderEveryone()は同じファイルを見ているため）。
    ・エントリを一意に特定するキーは、専用のidを新設せず既存の"time"
      （秒単位で記録される日時。本人の記録内で衝突する心配は実質無い）を使う。
      これにより、この機能を追加する前からあった過去のログもそのまま削除できる。
    """
    data = request.json or {}
    guild_id, student_id, nickname, err = require_login_json(data)
    if err:
        return err
    time_key = data.get("time")
    if not time_key:
        return jsonify({"ok": False, "error": "missing time"})

    logs = load_study_logs(guild_id)
    target = next((l for l in logs if l.get("student_id") == student_id and l.get("time") == time_key), None)
    if not target:
        return jsonify({"ok": False, "error": "log not found"})

    new_logs = [l for l in logs if l is not target]
    try:
        save_study_logs(guild_id, new_logs)
    except DataWriteError as e:
        return jsonify({"ok": False, "error": f"local_write_failed: {e}"})
```
- 関数冒頭のコメントに、設計判断が過不足なくまとめられています。特に重要なのは「本人の記録以外は削除できない」という制約で、これは`target`を探す条件に`l.get("student_id") == student_id`（セッションから特定した、リクエストを送った本人のID）を必ず含めていることで実現されています。他人の`time`キーを知っていても、`student_id`が一致しなければそのログは`target`として見つからず、削除できません。
- `new_logs = [l for l in logs if l is not target]`… `l is not target`という比較に注目してください。`==`（値が等しいか）ではなく`is`（**同じオブジェクトそのものかどうか**）で比較しています。これにより、万一内容が完全に同じログが複数存在していても、`next(...)`で最初に見つけた**その1件だけ**を確実に取り除くことができます（`==`で比較していたら、内容が同じ複数のログが誤って全部消えてしまう可能性があります）。

```python
    earned = (target.get("minutes") or 0) // 5
    pts = load_points(guild_id)
    pts[student_id] = max(0, pts.get(student_id, 0) - earned)
    try:
        save_points(guild_id, pts)
    except DataWriteError as e:
        return jsonify({"ok": False, "error": f"local_write_failed: {e}"})

    change = _diff_study_logs(f"study_logs_{guild_id}.json", logs, new_logs)
    log_event(
        "study",
        f"学習ログ「{target.get('subject')}」を削除しました（{target.get('minutes')}分・{earned}pt減算）。",
        actor=nickname,
        detail=[change] if change else None,
    )
    return jsonify({"ok": True, "total": pts[student_id]})
```
- 削除する記録が獲得していたポイント数を計算し直し、累計から差し引きます。`max(0, ...)`で、万一の計算のズレがあっても**マイナスのポイントにはならない**ように下限を0にガードしています。

## 2. `/list_schedule`：予定一覧の取得とページング（2492〜2540行）

```python
@app.route("/list_schedule", methods=["GET"])
def list_schedule():
    """
    ★ scope 未指定時は従来通り全件を返す（互換性を保つため）。
    ・scope=future : 今日以降の予定を全件（日付昇順）で返す。
    ・scope=past   : 今日より前の予定を、直近の過去から順（日付降順）に
      offset/limit でページングして返す。
    """
    guild_id = request.args.get("guild_id")
    if not guild_id:
        return jsonify({"ok": False, "error": "missing guild_id"})
    guild_id = int(guild_id)
    if not resolve_session(session_token_from_request(), guild_id):
        return jsonify({"ok": False, "error": "not_logged_in"})
    plans = sorted(load_plans(guild_id), key=lambda p: p["date"])
```
- コメントの通り、**予定の閲覧にも今はログインが必須**です。ただし[../05_ユーザーとセッション/01_セッショントークンと権限チェック.md](../05_ユーザーとセッション/01_セッショントークンと権限チェック.md)で見た通り、これは`require_member_session`ではなく`resolve_session`だけを使っています（＝制限付きアカウントでも閲覧できる、唯一の機能です）。

```python
    scope = request.args.get("scope")
    if not scope:
        return jsonify({"ok": True, "plans": plans})

    today_str = datetime.now(JST).strftime("%Y-%m-%d")
    if scope == "future":
        future = [p for p in plans if p["date"] >= today_str]
        return jsonify({"ok": True, "plans": future})

    if scope == "past":
        past = [p for p in plans if p["date"] < today_str]
        past.reverse()  # 直近の過去から順
        try:
            offset = max(0, int(request.args.get("offset", 0)))
            limit  = max(1, min(200, int(request.args.get("limit", 50))))
        except (TypeError, ValueError):
            return jsonify({"ok": False, "error": "invalid offset/limit"})
        page = past[offset: offset + limit]
        return jsonify({
            "ok": True,
            "plans": page,
            "total": len(past),
            "has_more": offset + limit < len(past),
        })

    return jsonify({"ok": False, "error": "invalid scope"})
```
- `scope`引数によって、返す予定の範囲を変えられます。
  - 指定無し… 従来通り全件（互換性のため。呼び出し元を全部書き換えなくても、これまで通りの動きを保証しています）。
  - `"future"`… 今日以降の予定を全部、日付が古い順に返します。コメントの通り「未来の予定はそこまで多くならない」という前提で、ページングはしていません。
  - `"past"`… 今日より前の予定を、**直近の過去から順**（`past.reverse()`で日付の新しい方が先頭に来るようにする）に、`offset`/`limit`で**ページング**（一部分だけを少しずつ返す）します。コメントにある背景が重要です：「予定を自動削除しなくなった分、過去分は年月とともに増え続ける」ため、一覧画面では「これからの予定を先に全部表示し、過去分は少しずつ追加読み込みする」という使い方を想定しています。
  - `page = past[offset: offset + limit]`… Pythonのスライス構文で、`offset`番目から`limit`件分だけを切り出します。
  - `"has_more": offset + limit < len(past)`… 「今回返した分の続きが、まだ残っているかどうか」を明示的に返します。フロント側はこれを見て「もっと読み込む」ボタンを表示するかどうかを判断します。
  - `offset`/`limit`は`max`/`min`で範囲を強制し（`limit`は最大200件まで）、数値として不正な値が渡された場合は`invalid offset/limit`エラーを返します。

## 3. `/edit_schedule`・`/delete_schedule`：予定の編集/削除（2544〜2670行）

これらは、[../07_Discordコマンド/01_list_delete_editコマンド.md](../07_Discordコマンド/01_list_delete_editコマンド.md)で見たDiscordコマンド版の`/edit`・`/delete`と、ほぼ同じロジックのWeb版です。異なる点だけ挙げます。

- **ログイン確認が入る**… 冒頭で必ず`require_login_json(data)`を呼び、`nickname`もサーバー側から取得し直します（Discordコマンド版は、Discord上でコマンドを実行できている時点で本人確認済みなので、この手続きは不要でした）。
- **`points`の扱いに`try`/`except`が追加されている**… `edit_schedule`では`new_points`が`data.get("points")`としてWebのフォームから文字列や不正な値で送られてくる可能性があるため、`int(new_points)`への変換を明示的に検証しています（Discordコマンド版は、discord.pyの型システムが引数の型を`int`として保証してくれるため、この検証が元々不要でした）。
- **運用ログ（`log_event`）への記録が追加されている**… `write_log`（古い簡易ログ）に加えて、`file_diff`で作った差分付きで`log_event`（新しい運用ログ）にも記録しています。これは前の回で見たWeb版`/add_schedule`と同じパターンです。
- **Discordへの通知は`run_coroutine_threadsafe`経由**… [00_チャンネル一覧と予定の追加API.md](00_チャンネル一覧と予定の追加API.md)の`/add_schedule`で解説した通り、Flask側（同期処理）からDiscord Bot側（非同期のイベントループ）にメッセージ送信を依頼する際は、必ず`asyncio.run_coroutine_threadsafe(コルーチン, bot.loop).result(timeout=10)`という橋渡しを経由します。

`delete_schedule`の`for p in plans: ... else: new_plans.append(p)`という「削除対象以外を新しい配列に集め直す」パターンも、[../07_Discordコマンド/01_list_delete_editコマンド.md](../07_Discordコマンド/01_list_delete_editコマンド.md)の`/delete`コマンドと全く同じ考え方です。

## 4. `/list_logs`：簡易ログの一覧取得（2672〜2701行）

```python
@app.route("/list_logs", methods=["GET"])
def list_logs():
    """
    ★ offset/limit 未指定時は従来通り全件を返す（互換性維持）。
      指定された場合は、新しい順に並んだログを offset/limit でページングして
      返す（has_more で続きの有無を伝える）。
    """
    guild_id = request.args.get("guild_id")
    if not guild_id:
        return jsonify({"ok": False, "error": "missing guild_id"})
    logs, _ = local_get(f"logs_{guild_id}.json")
    logs = sorted(logs or [], key=lambda l: l["time"], reverse=True)

    if request.args.get("offset") is None and request.args.get("limit") is None:
        return jsonify({"ok": True, "logs": logs})

    try:
        offset = max(0, int(request.args.get("offset", 0)))
        limit  = max(1, min(200, int(request.args.get("limit", 50))))
    except (TypeError, ValueError):
        return jsonify({"ok": False, "error": "invalid offset/limit"})
    page = logs[offset: offset + limit]
    return jsonify({
        "ok": True,
        "logs": page,
        "total": len(logs),
        "has_more": offset + limit < len(logs),
    })
```
- [../03_予定と時間割データ層/00_予定データとログ記録.md](../03_予定と時間割データ層/00_予定データとログ記録.md)で見た、`write_log`で書き込まれる古い方の簡易ログ（`logs_{guild_id}.json`）を取得するAPIです。`/list_schedule`の`scope=past`と全く同じ考え方のページング（`offset`/`limit`・`has_more`）が使われています。
- `sorted(logs or [], key=lambda l: l["time"], reverse=True)`… `time`（記録時刻の文字列）を基準に、新しい順（`reverse=True`）に並び替えます。日付・時刻の文字列は`YYYY-MM-DD HH:MM:SS`という形式で保存されているため、文字列としての並び替えがそのまま時系列の並び替えとして機能します。
