# セッショントークンと権限チェック（`bot.py` 1159〜1309行）

対象：`bot.py`の「ログインセッション」「サーバー参加者限定の権限チェック」「変更系API共通のログイン必須チェック」セクション。このシリーズで最もセキュリティに関わる部分の1つです。デスクトップの`1I勉強会webの裏側（設計の話）.md`の「1.3 セッション（ログイン状態）の仕組み」で説明されている内容の、**実際のコード**がここにあります。

## 1. なぜ「署名付きトークン」方式なのか（コメントより）

最初は「サーバーのメモリ上に、発行済みトークンの一覧を持つ」という素朴な方式で作られていました。しかし、以前使っていたRenderという無料のホスティングサービスは、一定時間アクセスが無いとプロセスごと再起動されてしまう仕様があり、そうなるとメモリの中身（＝発行済みトークン一覧）がまるごと消えてしまいます。結果として「少し間を空けてアクセスしただけで全員ログアウトされる」という、実用上まずい挙動になっていました。

そこで、トークンそのものの中に`guild_id`・`student_id`・発行時刻を埋め込み、**HMAC署名**を付けて改ざんを検知する方式に変更されています。これはJWT（JSON Web Token）と呼ばれる技術の簡易な自作版のようなものです。サーバーが何も覚えていなくても、トークン自体を見るだけで「本物かどうか」「誰のものか」「いつ発行されたか」が分かるため、プロセスの再起動に影響されません。

```python
SESSION_SECRET = os.getenv("SESSION_SECRET")
if not SESSION_SECRET:
    SESSION_SECRET = secrets.token_hex(32)
    print("[WARN] 環境変数 SESSION_SECRET が未設定です。...")

SESSION_TTL_SEC = 60 * 60 * 24 * 30  # 30日間ログイン状態を維持
```
- `SESSION_SECRET`… HMAC署名を作るための秘密鍵です。環境変数に設定するのが推奨されており、未設定の場合は`secrets.token_hex(32)`（暗号学的に安全なランダムな文字列を生成する標準ライブラリの関数）でその場限りの値を作りますが、その場合プロセスが再起動されるたびに鍵が変わってしまうため、結局全員ログアウトされてしまいます（が、パスワードそのものが漏れることはありません、という注記です）。
- `SESSION_TTL_SEC`… トークンの有効期限（TTL = Time To Live）で、30日間です。

```python
SESSION_MIN_ISSUED_AT = datetime(2026, 8, 20, 0, 0, 0, tzinfo=JST).timestamp()
```
- コメントによると、これは2026/08/20にログイン方式をパスワード認証からDiscordログインへ一本化した際の、**一度きりの移行措置**です。この日時より前に発行されたセッショントークンは、（旧パスワード方式を経由していた可能性があるものを含めて）無条件に無効として扱われます。
- コメントの注意書きが特に重要です：「今日の0時」より前を切り捨てる設計であり、もし誤って「明日の0時」のような未来の時刻にしてしまうと、この変更を適用した**直後に新しくログインし直したユーザーのセッションまで即座に無効判定されてしまう**という事故になります（発行時刻がその未来の時刻を下回ってしまうため）。実際の実装は必ず「今日または過去」の固定日時にする必要がある、という教訓がコメントとして残されています。
- また、`time.time()`（現在時刻）を直接使わずに固定の日時にしてあるのも意図的です。もし現在時刻を基準にしてしまうと、プロセスが再起動されるたびにこの基準時刻も動いてしまい、結果的に全員が毎回ログアウトされることになってしまいます。

## 2. トークンの発行と検証（1204〜1228行）

```python
def create_session(guild_id: int, student_id: str) -> str:
    payload = json.dumps({"g": guild_id, "s": student_id, "t": int(time.time())}, separators=(",", ":"))
    payload_b64 = base64.urlsafe_b64encode(payload.encode()).decode()
    sig = hmac.new(SESSION_SECRET.encode(), payload_b64.encode(), hashlib.sha256).hexdigest()
    return f"{payload_b64}.{sig}"
```
- `payload`… `{guild_id, student_id, 発行時刻}`を、キーを短く省略した(`g`/`s`/`t`)JSON文字列にします。`separators=(",", ":")`は、スペースを入れない詰めた形式で出力する指定です（トークンをできるだけ短くするため）。
- `base64.urlsafe_b64encode(...)`… このJSON文字列を、URLの中に安全に含められる文字だけの形式（Base64のURLセーフ版。`+`や`/`のようなURLで特別な意味を持つ文字を使わない）に変換します。
- `hmac.new(SESSION_SECRET.encode(), payload_b64.encode(), hashlib.sha256).hexdigest()`… `payload_b64`（変換後の中身）に対して、秘密鍵`SESSION_SECRET`を使ったHMAC-SHA256という署名を計算します。HMACとは「秘密鍵を知っている人だけが、正しい署名を作れる」仕組みです。秘密鍵を知らない第三者は、たとえ`payload_b64`の中身を推測・改ざんできても、対応する正しい署名までは作れません。
- 最終的なトークンは`"中身.署名"`という形の1本の文字列です。

```python
def resolve_session(token, guild_id: int):
    if not token or "." not in token:
        return None
    try:
        payload_b64, sig = token.rsplit(".", 1)
        expected_sig = hmac.new(SESSION_SECRET.encode(), payload_b64.encode(), hashlib.sha256).hexdigest()
        if not hmac.compare_digest(sig, expected_sig):
            return None
        payload = json.loads(base64.urlsafe_b64decode(payload_b64.encode()).decode())
        if payload.get("g") != guild_id:
            return None
        if time.time() - payload.get("t", 0) > SESSION_TTL_SEC:
            return None
        if payload.get("t", 0) < SESSION_MIN_ISSUED_AT:
            return None
        return payload.get("s")
    except Exception:
        return None
```
- トークンを検証し、有効なら`student_id`を、無効なら`None`を返す関数です。以降のほぼ全てのログイン確認処理は、最終的にこの関数にたどり着きます。
- `token.rsplit(".", 1)`… 右側から最初の`.`で1回だけ分割し、`payload_b64`（中身）と`sig`（送られてきた署名）に分けます。
- `expected_sig = hmac.new(...)`… 受け取った`payload_b64`から、正しい署名を**サーバー側で改めて計算し直します**。
- `hmac.compare_digest(sig, expected_sig)`… 送られてきた署名と、計算し直した署名が一致するか比較します。ここで単純に`sig == expected_sig`と書かない理由が重要です。`compare_digest`は**タイミング攻撃**（比較にかかる時間のわずかな差から、正解の文字列を1文字ずつ推測していく攻撃手法）を防ぐために設計された、常に一定の時間で比較する専用の関数です。もし単純な`==`比較を使うと、一致する文字数が多いほど比較に時間がかかる（多くの言語処理系では先頭から一致しない文字が見つかった時点で比較を打ち切るため）ことを利用して、署名を1バイトずつ割り出されてしまう可能性が理論上あります。
- 署名が一致すれば、`payload_b64`をデコードして中身（`payload`）を取り出し、さらに3つのチェックを行います。
  1. `payload.get("g") != guild_id`… トークンに埋め込まれたguild_idが、今アクセスしようとしているguild_idと一致するか（他のサーバー用に発行されたトークンの使い回しを防ぐ）。
  2. `time.time() - payload.get("t", 0) > SESSION_TTL_SEC`… 発行から30日（`SESSION_TTL_SEC`）以上経過していないか（期限切れチェック）。
  3. `payload.get("t", 0) < SESSION_MIN_ISSUED_AT`… 前述の「2026/08/20より前に発行されたトークンを一括で無効化する」チェック。
- どこか1つでも引っかかれば`None`を返し、全て通れば`payload.get("s")`（学籍番号）を返します。
- 関数全体が`try`/`except Exception`で囲まれており、トークンの形式が壊れている・デコードできない・改ざんされているなど、あらゆる異常なケースで安全に`None`（＝ログインしていない扱い）を返すようになっています。「よく分からないエラーで500エラーになってサーバーが落ちる」ようなことがなく、常に「無効なトークン」として穏当に処理されるという安全設計です。

```python
def session_token_from_request():
    auth = request.headers.get("Authorization", "")
    if auth.startswith("Bearer "):
        return auth[len("Bearer "):]
    return request.args.get("session_token")
```
- GET系APIから、セッショントークンを取り出すためのヘルパーです。コメントにある通り、以前はURLのクエリ文字列（`?session_token=...`）にトークンを載せていましたが、これだとブラウザの閲覧履歴・サーバーのアクセスログ・別サイトへ移動する際のReferer（参照元URL）にトークンが残ってしまうリスクがありました。
- 今は`Authorization: Bearer <token>`という、HTTPの標準的な認証用ヘッダーを優先して読み取ります。フロント側がまだ古い方式のままでも動くよう、ヘッダーが無い場合だけクエリ文字列にフォールバック（後方互換）します。

## 3. サーバー参加者限定の権限チェック（1243〜1275行）

コメントの通り、ログインをDiscordのみに一本化したのに合わせて追加された仕組みです。「対象Discordサーバーのメンバーではないログイン済みアカウント」を、完全にブロックするのではなく、**「閲覧はできるが編集は一切できない・見られる範囲も予定一覧のみ」という制限付きアカウント**として扱うことにした、というのがこの仕組みの目的です。

```python
def _session_is_member(guild_id: int, student_id: str) -> bool:
    login_links = load_discord_login_links(guild_id)
    discord_user_id = login_links.get(student_id)
    if not discord_user_id:
        return False
    return _guild_membership_status(guild_id, int(discord_user_id)) == "member"
```
- `student_id`（学籍番号）を、`discord_login_links`（ログイン専用の「学籍番号 ⇔ DiscordユーザーID」対応表）を使ってDiscordユーザーIDに変換し、そのユーザーが今も対象サーバーのメンバーかどうかを`_guild_membership_status`（Discord Bot側が持つメンバー一覧キャッシュを使って判定する関数。後の回で解説）で調べます。
- コメントにある通り、Discord連携が無い場合やBot側でまだ判定できない状況では、安全側に倒して`False`（メンバーではない扱い）を返します。「本当はメンバーなのに誤ってメンバーでないと判定してしまう」ことはあっても、その逆（本来メンバーでない人を誤ってメンバー扱いしてしまう）は起きない設計です。

```python
def require_member_session(token, guild_id: int):
    """戻り値 (student_id, err)。err が None でなければ呼び出し側はそのまま `return err` してよい。"""
    student_id = resolve_session(token, guild_id)
    if not student_id:
        return None, jsonify({"ok": False, "error": "not_logged_in"})
    if not _session_is_member(guild_id, student_id):
        return None, jsonify({"ok": False, "error": "guild_membership_required"})
    return student_id, None
```
- `resolve_session`によるトークン検証と、`_session_is_member`によるメンバーシップ確認の**両方**を行う、より厳格なチェック関数です。
- コメントにある通り、ログインしていない場合（トークンが無効）は`"not_logged_in"`、ログインはしているがメンバーではない場合は`"guild_membership_required"`という、**意図的に別々のエラーコード**を返します。これは、フロント側がこの2つを区別できるようにするためです。もし両方とも同じエラーコードにしてしまうと、フロント側が「ログインしていない」と誤解して、既にログイン済みのユーザーを強制的に再ログイン画面に飛ばしてしまう（`forceReLogin()`のような処理を誤発動させる）可能性があります。「ログインはできているが権限が制限されている」という状態を、「ログインできていない」という状態ときちんと区別することが、良いユーザー体験のために必要という判断です。
- コメントにある通り、唯一の例外として`/list_schedule`（予定一覧の閲覧）だけは、この`require_member_session`を使わず、従来通り`resolve_session`だけで判定します。これが「制限付きアカウントでも見られる唯一の機能」です。

## 4. 「変更」系API共通のログイン必須チェック：`require_login_json`（1277〜1308行）

```python
def require_login_json(data):
    """POST系「変更」API共通：JSONボディのguild_id・session_tokenを検証する。
    戻り値 (guild_id, student_id, nickname, err)。err が None でなければ、
    呼び出し側はそのまま `return err` してよい。"""
    guild_id = data.get("guild_id")
    if not guild_id:
        return None, None, None, jsonify({"ok": False, "error": "missing guild_id"})
    try:
        guild_id = int(guild_id)
    except (TypeError, ValueError):
        return None, None, None, jsonify({"ok": False, "error": "invalid guild_id"})
    student_id, err = require_member_session(data.get("session_token"), guild_id)
    if err:
        return None, None, None, err
    user = find_user(guild_id, student_id)
    nickname = user["nickname"] if user else None
    return guild_id, student_id, nickname, None
```
- これが、このあとFlask APIの章で繰り返し登場する、**最も頻繁に使われる認証ヘルパー**です。[[../../1I勉強会web解説/02_Cardmaker/03_Cardmaker.js_その3_デッキの読み込みと作成編集.md]]など、フロント側の解説でも度々「サーバー側で`require_login_json`により検証される」という形で名前が登場していた関数の、実体がここにあります。
- コメントにある背景説明が重要です。以前は予定・時間割・カードデッキ・フォルダ・お知らせの追加/編集/削除系APIが、ログイン確認をせず**クライアントが自己申告してきた`nickname`をそのまま信用していました**。つまり、ログインしていなくても、Web上の画面を経由せずAPIを直接叩けば、誰でも好きな名前を名乗って予定を追加したり削除したりできてしまっていた、ということです。この関数は、その脆弱性を塞ぐために追加された、**全ての「変更」系APIで統一的にログインを必須にする**ための共通処理です。
- `guild_id`の存在チェック・整数への変換チェックを行った後、`require_member_session`でセッションとメンバーシップの両方を検証します。
- **`nickname`はクライアントからの自己申告を一切使わず、`find_user`でサーバー側のユーザーデータから改めて引き直しています**。これは表示名の詐称（自分の本当のニックネームとは違う、他人になりすました名前を名乗ること）を防ぐための、もう1つの重要な対策です。
- コメントの最後にある通り、2026/08/20の追加で「変更は編集そのものなので、ログイン済みだけでなく対象サーバーのメンバーであることも必須にした」という経緯で、内部で使う関数が`resolve_session`だけの緩い版から、`require_member_session`（メンバーシップ確認込み）に変わっています。
