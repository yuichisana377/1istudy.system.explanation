## 1. DM送信の共通処理：`send_discord_dm`（3452〜3476行）

```python
def send_discord_dm(guild_id: int, student_id: str, title: str, message: str):
    """
    ・連携していない場合は ValueError("not_linked") を送出する。
    ・★ 追加（2026/08/20）：対象サーバーのメンバーではない場合も同じ
      ValueError("not_linked") を送出する（＝制限付きアカウントには
      DM機能を一切使わせない方針。呼び出し側は元々「連携していない」
      場合のフォールバック処理を持っているため、そのまま流用できる）。
    ・送信自体に失敗した場合はその例外をそのまま送出する。
    """
    links = load_discord_links(guild_id)
    discord_user_id = links.get(str(student_id).strip().upper())
    if not discord_user_id:
        raise ValueError("not_linked")
    if _guild_membership_status(guild_id, int(discord_user_id)) != "member":
        raise ValueError("not_linked")

    async def _send():
        user = bot.get_user(int(discord_user_id))
        if user is None:
            user = await bot.fetch_user(int(discord_user_id))
        await user.send(f"**{title}**\n{message}")

    future = asyncio.run_coroutine_threadsafe(_send(), bot.loop)
    future.result(timeout=10)
```
- これが、これまでの回で何度も名前が登場していた、**DM送信の唯一の窓口**です。[../04_勉強タイマー/00_勉強タイマーの状態管理.md](../04_勉強タイマー/00_勉強タイマーの状態管理.md)の`_try_notify_timer`、[../07_Discordコマンド/03_id連携とhelpコマンド.md](../07_Discordコマンド/03_id連携とhelpコマンド.md)の確認DM、[01_OAuthコールバックと初回登録.md](01_OAuthコールバックと初回登録.md)の連携完了DMなど、Bot からのDM送信は全てこの関数を経由します。
- コメントの通り、**同じ`ValueError("not_linked")`という例外が、実は2つの異なる理由（連携していない／メンバーではない）から発生しうる**という設計になっている点が興味深いところです。あえて理由を分けずに1つの例外に統一しているのは、コメントにある通り「呼び出し側は元々『連携していない』場合のフォールバック処理を持っているため、そのまま流用できる」という理由です。制限付きアカウントに対しては、新しく専用のエラーハンドリングを追加する必要が無く、既存の「未連携」の処理パスにそのまま乗せられるという、変更を小さく抑えるための実用的な判断です。
- `bot.get_user(...)`（キャッシュから取得。無ければ`None`）→`bot.fetch_user(...)`（キャッシュに無ければ、改めてDiscordのAPIに問い合わせて取得）という2段構えになっています。これは、頻繁に使うキャッシュを優先しつつ、キャッシュに無い場合でも確実にユーザーを取得できるようにするパターンです。
- `asyncio.run_coroutine_threadsafe(_send(), bot.loop)`… [../09_FlaskAPI_予定管理/00_チャンネル一覧と予定の追加API.md](../09_FlaskAPI_予定管理/00_チャンネル一覧と予定の追加API.md)の`add_schedule`で見たのと同じ、Flask（同期）からDiscord Bot（非同期のイベントループ）へ処理を依頼する橋渡しです。この`send_discord_dm`自体は普通の同期関数なので、内部で非同期関数`_send`をその場で定義し、`run_coroutine_threadsafe`経由で実行しています。

## 4. 問題報告フォーム：`/report_problem`（3538〜3645行）

### 4-0. 追加の経緯（2026/08/21）：送信後に行き詰まる／報告が消える不具合

この機能は元々、「サイトのJSが完全に壊れて何もできない」という最悪の状況からの
唯一の連絡手段として作られたものですが、実際にJSを意図的に無効化して試した
利用者から、**この機能自体に2つの不具合**が見つかりました。

1. **送信後、サイトへ戻れなくなる**：`/report_problem`が返す結果ページ
   （`_report_problem_result_page`）には、以前は成功/失敗のメッセージしか
   無く、元のページへ戻るリンクが一切ありませんでした。JSが動く状態なら
   ブラウザの「戻る」機能等でなんとかなりますが、**JSが完全に壊れている
   ことを前提にした画面**なのに、その画面から先へまったく進めなくなる
   （唯一の脱出手段だったはずの機能が、逆に利用者を閉じ込めてしまう）
   という本末転倒な状態でした。
2. **DM送信に失敗すると、報告内容がそのまま消える**：以前の実装は
   `send_discord_dm`が失敗すると（管理者がDiscord未連携・対象サーバー未参加・
   一時的な通信エラーなど）、失敗メッセージを返すだけで、**報告の中身は
   どこにも残らず捨てられていました**。JSが壊れている状況では、この
   フォームが唯一の連絡手段のはずなのに、その唯一の手段がDM1回の成否に
   完全に依存してしまっていた、という設計上の弱点です。

この2点を修正したのが、以下で説明する`_sanitize_return_url`・
`_load_problem_reports`/`_save_problem_report`と、書き換え後の
`report_problem()`本体です。

### 4-1. `_sanitize_return_url`：戻り先URLの安全性チェック（3538〜3546行）

```python
def _sanitize_return_url(raw: str) -> str:
    raw = (raw or "").strip()
    if not raw.startswith("/") or raw.startswith("//") or ":" in raw:
        return "/"
    return raw[:200]
```
- 各ページのフォーム（後述）には、送信元のページを示す`return_url`という
  hidden fieldが新たに追加されました（例：`index.html`なら`/index.html`）。
  これを結果ページの「戻る」リンクの`href`にそのまま使いたいところですが、
  リクエストの中身は**常に外部から来る値として信用しない**のが原則です。
  もし`return_url`に`https://evil.example.com/`のような外部URLや、
  `//evil.example.com`のようなプロトコル相対URLを入れられてしまうと、
  「報告フォームの結果ページ経由で別のサイトへ誘導される」という
  **オープンリダイレクト**の脆弱性になり得ます。
- そこで、`/`から始まり（＝このサイト内の絶対パス）、`//`で始まらず
  （プロトコル相対URL除外）、`:`を含まない（`javascript:`のような
  スキームを使ったURLも除外）ものだけを通し、それ以外は問答無用で
  トップページ（`/`）に差し替えます。これにより、たとえ悪意ある値が
  送られてきても、行き先はこのサイトの中に限定されます。

  正規表現などで抜き出す、という方法も考えられますが、**表示用の文言と
  機能に使う値を同じ1つのフィールドに詰め込むと、表示文言を変えただけで
  機能が壊れる**という結合を生みやすいため、あえて別フィールドに分けて
  あります。
