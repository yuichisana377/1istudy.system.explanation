# 予定・簡易ログ・勉強ログのデータ層（`bot.py` 609〜748行）

対象：`bot.py`の「予定データ」「ログ」「勉強ログ データ」セクション。ここからしばらくは、[[02_データ保存基盤]]で作った土台を使って、機能ごとの「JSONファイルの読み書き」を行う関数が並びます。パターンがよく似ているので、読み方に慣れると理解が早くなります。

## 1. 予定データ（609〜645行）

```python
def load_plans(guild_id: int):
```

- `load_plans`/`save_plans`は`plans_{guild_id}.json`（予定一覧。宿題・提出・テストなど）を読み書きします。`data or []`で、ファイルが無ければ空のリストとして扱います。
- `save_plans`の最後で`notify_change(guild_id)`を呼んでいる点に注目してください。これが[[../01_起動と初期設定/00_設定の読み込みとFlask_Discordの初期化.md]]で解説したSSE通知です。予定が保存されるたびに、そのguildを見ている全てのブラウザタブへ「変わったよ」の合図が飛び、予定一覧ページがリアルタイムで更新されます。

```python
def _plan_lines(p):
    fields = [

```
- `_plan_lines`は、予定1件を[[../02_データ保存基盤/01_運用ログとdiff表示.md]]で解説した`_json_block`を使って、運用ログ表示用の`{ ... }`ブロックに変換します。`p.get("points")`（この予定に紐づくポイント）が設定されている場合だけ、その行を追加します（`if`で条件付きに`fields`へ足しています）。
- `_plans_text`は、予定の配列全体を1本のテキストに変換します（各予定の`_plan_lines`の結果を`lines`に次々足し込み、最後に改行で連結）。これは、予定一覧全体の「変更前」「変更後」を比較して差分を取るために使われます（後述の`add_schedule`などのFlask APIで実際に使われます）。

## 2. 簡易ログ：`write_log`（646〜672行）

```python
def write_log(guild_id: int, log_type: str, detail: str):
    try:
        filename = f"logs_{guild_id}.json"
        logs, sha = local_get(filename)
        logs = logs or []
        now_jst = datetime.now(JST)
        now_str = now_jst.strftime("%Y-%m-%d %H:%M:%S")
        logs = [
            log for log in logs
            if (now_jst - datetime.strptime(log["time"], "%Y-%m-%d %H:%M:%S").replace(tzinfo=JST)).days <= 30
        ]
        logs.append({"time": now_str, "type": log_type, "detail": detail})
        local_put(filename, logs, sha)
    except Exception as e:
        print(f"[WARN] write_log failed (ignored): {e}")
```
- これは[[../02_データ保存基盤/01_運用ログとdiff表示.md]]で解説した`log_event`（`system_log.json`、差分付きの新しい運用ログ）とは**別物**です。`logs_{guild_id}.json`というguildごとのファイルに、`{"time", "type", "detail"}`という単純な形式で記録される、より古くからある内部用の簡易ログです。コメントにある通り、今は`log_event`の方がより詳しい実装として使われており、こちらはほぼ役目を終えつつありますが、コード上はまだ残っています。
- `logs = [log for log in logs if (今の時刻 - その記録の時刻).days <= 30]`… **30日より古い記録は、新しい記録を追加する直前に自動的に間引かれます**（ロールオーバー）。これにより、ファイルが無限に肥大化するのを防いでいます。
- `datetime.strptime(log["time"], "%Y-%m-%d %H:%M:%S")`… 文字列として保存されている時刻を、計算できる`datetime`オブジェクトに戻す処理です（`strftime`の逆で、`strptime`は「文字列をパースする（解析する）」の意味）。
- 関数全体が`try`/`except`で囲まれており、コメントにある通り「ログ保存の失敗は本質的な機能ではないので、例外を握りつぶしてよい」という判断です。ただし、原因調査ができるように`print`で標準出力には残します。

```python
def _study_log_lines(l):
    fields = [
        ("記録日時", l.get('time')),
        ("実行者", l.get('nickname')),
        ("科目", l.get('subject')),
        ("時間", f"{l.get('minutes')}分"),
        ("メモ", l.get('memo') or "(なし)"),
    ]
    return _json_block(fields)

def _study_log_key(l, idx):
    if isinstance(l, dict) and l.get("time"):
        return l["time"]
    return f"__pos_{idx}"
```
- `_study_log_lines`は勉強ログ1件を運用ログ用のブロックに変換します（予定と同じ考え方）。
- `_study_log_key`は、勉強ログ1件1件を見分けるための「キー」を作る関数です。勉強ログには専用のID（連番など）が振られていないため、代わりに`time`（秒単位の記録日時）を安定した見分け用のキーとして使っています。もし`time`が無い異常なデータの場合は`f"__pos_{idx}"`（配列内の位置番号）を代わりに使います。

```python
def _diff_study_logs(file, old_logs, new_logs, max_lines=40):
    old_logs = old_logs or []
    new_logs = new_logs or []
    old_by_key = {_study_log_key(l, i): l for i, l in enumerate(old_logs) if isinstance(l, dict)}
    new_by_key = {_study_log_key(l, i): l for i, l in enumerate(new_logs) if isinstance(l, dict)}

    lines = []
    for key, l in new_by_key.items():
        if key not in old_by_key:
            lines.extend(f"+ {ln}" for ln in _study_log_lines(l))
    for key, l in old_by_key.items():
        if key not in new_by_key:
            lines.extend(f"- {ln}" for ln in _study_log_lines(l))

    if not lines:
        return None
    if len(lines) > max_lines:
        lines = lines[:max_lines] + [f"…ほか{len(lines) - max_lines}行"]
    return {"file": file, "diff": "\n".join(lines), "status": "modified"}
```
- コメントに書かれている通り、この関数には**過去に実際に起きた不具合の修正の経緯**が記録されています。以前は「変更前と変更後をそれぞれ1本の長いテキストにしてから、テキスト全体としての行差分（`difflib`）を取る」という方式で作られていましたが、勉強ログの各エントリは`_json_block`で作られる`{ `や`}`のような**見た目が完全に同じ行**を含むため、テキスト差分アルゴリズムが「削除された1件の`{`」と「別の生き残っているエントリの`{`」を誤って対応付けてしまい、結果として「メモ: ｝｛」のような中身が化けたような表示になる不具合が実際に起きました（ユーザーからの実際の報告がきっかけで発覚・修正されています）。
- 修正後のこのコードは、**テキストとしての差分ではなく、キー（`_study_log_key`）を使ってエントリそのものを1件ずつ突き合わせる**方式に直っています。
  - `old_by_key`/`new_by_key`… `{キー: そのエントリ}`という辞書に変換します（辞書内包表記）。`isinstance(l, dict)`で、万一配列内に壊れたデータ（辞書でない要素）が混ざっていても無視するようにしています。
  - 新しい方にだけあるキー（`key not in old_by_key`）→ そのエントリは「追加された」ので`+`付きの行として`lines`に足します。
  - 古い方にだけあるキー（`key not in new_by_key`）→ そのエントリは「削除された」ので`-`付きの行として足します。
  - コメントにある通り、勉強ログには今のところ「編集」機能が無く「追加」「削除」しか無いため、`_diff_deck_cards`（カードデッキの差分。後の回で解説）のような「内容が変わった同じキーのエントリを比較する」分岐は、まだここには存在しません。
- 最後の`status`は常に`"modified"`固定です。コメントの通り、`study_logs_{guild_id}.json`自体は生徒全員で共有する既存ファイルであり、ここでの「追加/削除」はあくまで**ファイルの中の1エントリ単位**の追加/削除であって、ファイル自体が新規作成/削除されるわけではないため、[[../02_データ保存基盤/01_運用ログとdiff表示.md]]で解説した`file_diff`の`status`（ファイル単位の"added"/"deleted"）とは意味が違う、という点に注意が必要です。
