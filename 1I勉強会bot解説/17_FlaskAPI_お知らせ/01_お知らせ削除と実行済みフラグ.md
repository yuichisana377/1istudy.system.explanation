# お知らせの削除と「実行済み」フラグ（`bot.py` 5924〜6039行）

対象：`bot.py`の`_notice_owner`・`_delete_notice_file`・`/delete_notice`・「Flask API — お知らせの『実行済み』（全員共有）」セクション。これで「Flask API — お知らせ」の章が終わります。

## 1. 投稿者の判定と削除処理（5924〜5970行）


- [[../14_FlaskAPI_CardMaker/02_デッキ削除と作成者確認.md]]の`_deck_owner`と全く同じ構造です。CardMakerでは`published_by.id`をデッキ本体のファイルから読んでいましたが、お知らせでは`notices_meta.json`という別ファイルから`uploader_id`を読む、という違いがあります（お知らせ本文自体はプレーンテキストなので、そこにメタ情報を混ぜて持たせることができないためです）。

```python
def _delete_notice_file(filename, actor_nickname, approval_note=None):
    """お知らせファイル削除の実処理（本人による直接削除・削除依頼の承認の
    どちらからも呼ばれる共通処理）。作成者チェックは呼び出し側の責務。"""
    path = _data_path(f"{NOTICES_DIR}/{filename}")
    if not os.path.isfile(path):
        return jsonify({"ok": False, "error": "ファイルが見つかりません"})
    try:
        with open(path, "r", encoding="utf-8") as f:
            deleted_content = f.read()
    except OSError:
        deleted_content = None
    try:
        os.remove(path)
    except OSError as e:
        return jsonify({"ok": False, "error": f"local_delete_failed: {e}"})

    meta_change = None
    try:
        meta, meta_sha = load_notices_meta()
        if filename in meta:
            old_meta_entry = meta[filename]
            del meta[filename]
            save_notices_meta(meta, meta_sha)
            meta_change = _notice_meta_entry_diff(filename, old_meta_entry, None)
    except DataWriteError as e:
        print(f"[WARN] notices_meta からの削除に失敗しました: {e}")

    change = file_diff(f"{NOTICES_DIR}/{filename}", deleted_content, None)
    detail = [c for c in (change, meta_change) if c]
    summary = f"お知らせ「{filename}」を削除しました。"
    if approval_note:
        summary += approval_note
    log_event("notice", summary, actor=actor_nickname, detail=detail if detail else None)
    return jsonify({"ok": True})
```
- [[../14_FlaskAPI_CardMaker/02_デッキ削除と作成者確認.md]]の`_delete_card_deck_file`と、驚くほどよく似た構造です。「削除前に中身を控える（運用ログ用）」→「実ファイルを削除」→「関連するメタ情報も削除」→「差分をまとめて運用ログへ」という手順が、対象がカードデッキかお知らせかの違いだけで、ほぼ同じパターンとして繰り返されています。この関数も、コメントの通り「作成者チェックは呼び出し側の責務」であり、認可のロジックとは切り離されています。

## 2. `/delete_notice`：削除の入口（5972〜5994行）

```python
@app.route("/delete_notice", methods=["POST"])
def delete_notice():
    """お知らせファイルを削除する（メタ情報も合わせて削除）"""
    data = request.json or {}
    _guild_id, _student_id, nickname, err = require_login_json(data)
    if err:
        return err
    filename = data.get("filename", "")
    if not _is_safe_notice_filename(filename):
        return jsonify({"ok": False, "error": "invalid filename"})
    owner_id, owner_nickname = _notice_owner(filename)
    # ★ 2026/08/20 一旦revert：delete_cards側と同じ理由で、discord_links
    #   未紐づけを「孤立」とみなして自動で確認フローをスキップする判定は
    #   セキュリティ上の後退になるため外した（詳細はdelete_cards参照）。
    if owner_id and str(owner_id) != str(_student_id):
        return jsonify({
            "ok": False, "error": "creator_approval_required",
            "owner_nickname": owner_nickname or "投稿者",
        })
    return _delete_notice_file(filename, nickname)
```
- これも[[../14_FlaskAPI_CardMaker/02_デッキ削除と作成者確認.md]]の`/delete_cards`と全く同じ認可ロジックです。作成者本人以外の削除は`"creator_approval_required"`エラーで止められ、フロント側はこれを見て[[../12_FlaskAPI_削除依頼システム]]の`/request_delete`へ誘導します。コメントの中で明示的に`/delete_cards`側の判断を参照しており（「一旦revert」した経緯も含め）、**カードデッキとお知らせという2つの独立した機能が、同じ設計判断を共有している**ことが分かります。

## 3. `/set_notice_done`：実行済みフラグ（5997〜6039行）

### 設計方針（コメントより）

これはコメントの通り「生徒ごとではなく、みんなで1つの状態を共有する」機能です。誰か1人が実行済みにしたら、全員の一覧で下に移動・薄く表示されます（[[../06_Notice/00_HTML構造とその1_一覧と詳細表示.md|Web解説シリーズのNotice.js解説]]で見た挙動です）。既存の`notices_meta.json`（投稿者名など）に`"done"`フラグを追加するだけで、新しい保存先は増やしていません。

```python
@app.route("/set_notice_done", methods=["POST"])
def set_notice_done():
    data = request.json or {}
    _guild_id, _student_id, nickname, err = require_login_json(data)
    if err:
        return err
    filename = data.get("filename")
    done = bool(data.get("done"))
    if not _is_safe_notice_filename(filename):
        return jsonify({"ok": False, "error": "invalid filename"})
    try:
        last_err = None
        for _ in range(4):
            meta, sha = load_notices_meta()
            old_meta_text = _notices_meta_text(meta)
            entry = meta.get(filename, {})
            entry["done"] = done
            meta[filename] = entry
            try:
                save_notices_meta(meta, sha)
                change = file_diff(NOTICES_META_FILE, old_meta_text, _notices_meta_text(meta))
                log_event("notice", f"お知らせ「{filename}」を{'実行済み' if done else '未実行'}にしました。", actor=nickname, detail=[change] if change else None)
                return jsonify({"ok": True})
            except DataWriteError as e:
                last_err = e
                continue  # 他の端末の書き込みと競合した場合、最新を読み直してやり直す
        return jsonify({"ok": False, "error": f"local_write_failed: {last_err}"})
    except Exception as e:
        return jsonify({"ok": False, "error": str(e)})
```
- `for _ in range(4):`… [[../15_FlaskAPI_クイズ/02_ルーム作成と過去問ランキング.md]]の`_update_quiz_leaderboard`で見たのと同じ、**最大4回まで「読み直す→書き換える→保存を試みる」を繰り返す**、より丁寧な楽観的排他制御です。コメントの「他の端末の書き込みと競合した場合、最新を読み直してやり直す」という一文が、この設計の意図を端的に表しています。
- **なぜこの機能だけ、より丁寧なリトライが必要なのか**を考えると理解が深まります。「実行済みにする」というボタンは、[[../06_Notice/00_HTML構造とその1_一覧と詳細表示.md|Web解説シリーズ]]で見た通り、複数の生徒がほぼ同時に押す可能性が現実的にある操作です（例えば、全員が同じお知らせを見て「もう対応した」と押すタイミングが重なりやすい）。単純な「1回だけ無条件リトライ」（[[../02_データ保存基盤/00_ファイル読み書きとSHA排他制御.md]]の`local_put`のデフォルトの挙動）だと、3人以上が同時に操作した場合に、後発の操作が失敗し続ける可能性が上がります。そのため、ここでは`local_put`のデフォルトの排他制御を使わず、呼び出し側で明示的にリトライループを組んでいます。
- `entry = meta.get(filename, {})`… 万一メタ情報がまだ無い（アップロード時の記録に失敗していた等）場合でも、空の辞書から始めて`done`フラグだけは確実に設定できるようになっています。
