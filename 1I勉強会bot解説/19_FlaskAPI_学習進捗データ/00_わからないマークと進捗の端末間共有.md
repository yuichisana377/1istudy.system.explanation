# 学習データ（わからないマーク・続きから・完了記録）の端末間共有（`bot.py` 6328〜6564行）

対象：`bot.py`の「Flask API — 学習データ（わからないマーク／続きから／完了記録）の端末間共有」セクション。CardMakerで単語カードを学習する際の、生徒個人ごとの学習状況を扱うAPI群です。

## 設計方針（コメントより）

- 以前はブラウザの`localStorage`にしか保存しておらず、別の端末では見えませんでした。ログイン（`student_id`）に紐付けてサーバー側にも保存することで、同じアカウントでログインしていればどの端末からでも同じ状態を見られるようにします。
- `student_id`はタイマーAPIなどと同様、クライアントの自己申告を信用せず、必ず`session_token`から解決したものを使います。
- 1人分のデータ（`study_data_{guild_id}_{student_id}.json`）の中身は`{"unsure": {...}, "progress": {...}, "completed": {...}}`という形です。
- **全生徒分をまとめて1ファイルに保存する方式も検討されましたが、却下されています**。理由は「『わからない』マークはカードをめくるたびに更新が走りうるため、1ファイル共有だと生徒が増えるほどファイルへの書き込みが競合（409）しやすくなる」ためです。そのため**生徒ごとに別ファイルへ分け**、自分の学習データを保存するときは他の生徒の書き込みと衝突しないようにしています（本人の複数端末からの同時書き込みだけがぶつかる可能性があり、その場合は後述するリトライ処理でカバーされます）。この判断は、[[../04_勉強タイマー/00_勉強タイマーの状態管理.md]]で見た「guildごとの共有ファイル」とは対照的な、**書き込み頻度の高いデータは、あえてファイルを分割して競合自体を減らす**という設計判断です。

## 1. ファイル名の安全な生成（6352〜6362行）

```python
def _study_data_filename(guild_id: int, student_id: str) -> str:
    """
    ★ student_id はユーザー（先生）が自由な文字列で登録できてしまうため、
    そのままファイル名に使うと "/" 等でパスが変わってしまう恐れがある。
    英数字・ハイフン・アンダースコア以外は "_" に置き換えたうえで、
    末尾に短いハッシュを付けて衝突を防ぐ（安全性と可読性の両立）。"""
    safe = re.sub(r"[^A-Za-z0-9_-]", "_", str(student_id))[:40]
    suffix = hashlib.sha1(str(student_id).encode()).hexdigest()[:8]
    return f"study_data_{guild_id}_{safe}_{suffix}.json"
```
- これまでの多くの箇所では、`filename`が「クライアントから送られてくる」ために`"/"`や`".."`を弾くパストラバーサル対策が必要でした。この関数では逆に、**`student_id`という、サーバー自身が信頼している値からファイル名を組み立てる**という状況ですが、コメントの通り、`student_id`自体はユーザー（先生）が生徒データを登録する際に**自由な文字列として入力できてしまう**ため、油断はできません。
- `re.sub(r"[^A-Za-z0-9_-]", "_", ...)`… 正規表現を使って、英数字・ハイフン・アンダースコア**以外**の全ての文字を`_`に置き換えます。これにより、`student_id`にたとえ`/`や`..`のような危険な文字が含まれていても、ファイル名の一部としては無害な`_`に変換されてしまいます。
- `suffix = hashlib.sha1(...).hexdigest()[:8]`… 変換によって、本来別々だった2つの`student_id`（例えば`"1I/001"`と`"1I_001"`）が、変換後には同じ`"1I_001"`になってしまう可能性があります。これによるファイル名の衝突を避けるため、元の`student_id`から計算したハッシュ値の先頭8文字を、末尾に追加しています。ハッシュ値は元の文字列が少しでも違えば別の値になるため、変換後の文字列が同じになっても、末尾のハッシュが違えば別々のファイルとして区別できます。**「安全性（危険な文字を無害化する）」と「衝突回避（別々のデータが同じファイルに混ざらない）」を両立させる**、実務的なテクニックです。

## 2. データの読み書き（6361〜6378行）

```python
def _empty_student_study_data():
    return {"unsure": {}, "progress": {}, "completed": {}, "seen": {}}

def load_student_study_data(guild_id: int, student_id: str):
    data, sha = local_get(_study_data_filename(guild_id, student_id))
    if not data:
        return _empty_student_study_data(), sha
    return {
        "unsure":    data.get("unsure", {}),
        "progress":  data.get("progress", {}),
        "completed": data.get("completed", {}),
        "seen":      data.get("seen", {}),  # ★ 追加：「わかる率」集計用に、実際に表示した（学習した）カードキーをデッキごとに記録
    }, sha

def save_student_study_data(guild_id: int, student_id: str, data: dict, sha=None):
    local_put(_study_data_filename(guild_id, student_id), data, sha)
```
- `load_student_study_data`は、単に読み込んだデータをそのまま返すのではなく、**4つのフィールドそれぞれについて個別にデフォルト値（空の辞書）を補いながら**組み立て直しています。これにより、この機能が拡張されて新しいフィールド（`seen`など）が追加された際に、それ以前に保存された古いデータ（`seen`フィールドが無い）を読み込んでも、必ず`seen: {}`という形で補われ、呼び出し側は常に4つのフィールド全てが存在する前提でコードを書けます。

## 3. より丁寧な排他制御：`update_student_study_data`（6380〜6405行）

```python
def update_student_study_data(guild_id: int, student_id: str, mutate_fn, max_attempts: int = 4):
    """mutate_fn(my_data) は my_data を直接書き換える関数。
    保存に失敗（sha競合）した場合は最新データを読み直して再適用する。"""
    last_err = None
    for _ in range(max_attempts):
        my_data, sha = load_student_study_data(guild_id, student_id)
        mutate_fn(my_data)
        try:
            save_student_study_data(guild_id, student_id, my_data, sha)
            return
        except DataWriteError as e:
            last_err = e
            continue
    raise last_err or DataWriteError("保存に失敗しました（リトライ上限）")
```
- コメントに、**この排他制御が必要になった経緯**が書かれています：「以前は各APIハンドラが『リクエストの最初に読み込んだ`my_data`』をそのまま保存していたため、ほぼ同時に届いた別のリクエスト（例：『わからない』マークの保存と、カード送りのたびに自動で走る『続きから』進捗の保存）が競合すると、後から書き込んだ方が前の変更を含まない古い中身でファイル全体を上書きしてしまい、わからないマーク等の変更が消えてしまう不具合があった」。
- これは重要な教訓です。同じ生徒が、短時間のうちに「わからないマークを付ける」操作と「続きから」の自動保存を、ほぼ同時に（別々のAPIリクエストとして）行うと、**同じファイルに対する2つの独立した書き込みが競合**します。以前の実装は、単純に`local_put`の「1回だけ無条件リトライ」に頼っていたと考えられますが、これだけでは「先に読み込んだ古いデータに、自分の変更だけを加えて、丸ごと上書きする」形になり、その間に別のリクエストが加えた変更を消してしまいます。
- この`update_student_study_data`は、[[../15_FlaskAPI_クイズ/02_ルーム作成と過去問ランキング.md]]の`_update_quiz_leaderboard`や[[../17_FlaskAPI_お知らせ/01_お知らせ削除と実行済みフラグ.md]]の`/set_notice_done`と全く同じ「`mutate_fn`を、失敗するたびに最新データへ読み直して再適用する」パターンです。この生徒学習データが、これらと同様に**高頻度で競合しやすいデータ**として扱われていることが分かります。呼び出し側は「データをどう書き換えるか」だけを`mutate_fn`として渡せばよく、排他制御の複雑さはこの関数の中に隠蔽されています。

```python
@app.route("/deck_understanding", methods=["GET"])
def deck_understanding():
    """
    指定デッキ（複数可、カンマ区切り）について、自分だけでなく全生徒分を
    合算した「わかる率」を返す。
    ・「学習した（seen）カードのうち、今わからないマークが付いていない」割合。
    ・生徒ごとに別ファイル（study_data_{guild_id}_*.json）に分かれているため、
      対象ギルドの全ファイルを読んで合算する。"""
    ...
    prefix = f"study_data_{guild_id}_"
    studied = 0
    understood = 0
    try:
        names = os.listdir(DATA_DIR)
    except OSError:
        names = []
    for name in names:
        if not (name.startswith(prefix) and name.endswith(".json")):
            continue
        data, _ = local_get(name)
        if not data:
            continue
        seen_map   = data.get("seen", {}) or {}
        unsure_map = data.get("unsure", {}) or {}
        for fn in target_filenames:
            seen_keys = seen_map.get(fn)
            if not seen_keys:
                continue
            unsure_keys = set(unsure_map.get(fn) or [])
            studied += len(seen_keys)
            understood += sum(1 for k in seen_keys if k not in unsure_keys)
    return jsonify({"ok": True, "studied": studied, "understood": understood})
```
- これは「みんなのわかる率」を集計する、この章で唯一の**複数生徒のデータをまたぐ**APIです。「生徒ごとに別ファイルに分かれている」という前述の設計上の代償が、ここで表面化しています。全生徒分の合算値を出すには、**このguildの`study_data_`で始まる全ファイルを1つずつ開いて集計する**しかありません。コメントでは「ローカルディスクの読み込みなので生徒数が多くても軽い」とフォローされていますが、これは11人規模の運用を前提とした判断で、生徒数が数百人規模になれば、この総当たりの走査コストは無視できなくなってくるでしょう（このアプリの規模に見合った、現実的な設計判断です）。
- `os.listdir(DATA_DIR)`でデータディレクトリ全体を列挙し、`name.startswith(prefix)`（このguild用のファイルであるか）で絞り込みます。`_study_data_filename`が生成するファイル名の先頭部分（`study_data_{guild_id}_`）と一致するかどうかで判定しています。
- 各生徒のファイルについて、指定された`target_filenames`（デッキのファイル名、カンマ区切りで複数指定可）ごとに、`seen`（学習した）カード数を`studied`に、そのうち`unsure`（わからない）に含まれていないカード数を`understood`に積み上げていきます。全生徒分を合算した`studied`/`understood`の比率が、最終的な「わかる率」になります。
